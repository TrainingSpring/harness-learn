# 上下文与运行时架构更新迭代计划

## 1. 目标

本计划用于将当前项目调整为：

~~~text
Agent
= 独立、可复用的角色和能力定义

Session
= DIRECT/GROUP、成员关系、会话生命周期和 Context 的所有者

Context
= 一个 Session 的共享上下文，负责消息、工具结果、压缩、精简和恢复

Runtime
= Agent Loop，负责持续调用 LLM、处理工具和权限

ContextService
= 原始事件及当前实际 Context 的持久化
~~~

本计划只写文档，不代表代码已经完成。

## 2. 必须保持的不变量

1. Agent 不持有 Context、Session 或 ContextService。
2. 一个 Session 只有一个共享 Context。
3. GROUP 中所有 Agent 使用同一份 Context。
4. Runtime 保留 Agent Loop。
5. Runtime 通过 run(context) 使用 Context，但不将 Context 保存为实例属性。
6. Runtime 不直接访问数据库。
7. ContextService 不参与 Agent Loop。
8. 同一个 Agent 定义可以被多个 Session 使用。
9. 不同 Session 的 Context、ExecutionContext、Tools 执行环境和权限等待状态必须隔离。
10. 原始 context_items 不被压缩结果覆盖。
11. sessions.current_context_json 保存当前实际上下文。
12. DIRECT 和 GROUP 的差异由 Session 处理，不由 Agent、Tools、MCP 或 Skills 处理。

## 4. 生命周期模型

~~~text
AgentProfile
    ↓
AgentDefinition（可跨 Session 复用）
    ↓
Session A                         Session B
├── Context A                     ├── Context B
├── ExecutionContext A            ├── ExecutionContext B
├── Tools A                       ├── Tools B
├── Runtime 状态 A                ├── Runtime 状态 B
└── Permission 状态 A             └── Permission 状态 B
~~~

可以复用：

- AgentProfile
- AgentDefinition
- LLM 配置
- 工具定义和 schema
- Runtime 的执行算法

不能直接复用：

- Context
- ExecutionContext
- 绑定执行环境的 Tools
- pending permission
- tool queue
- 有状态 Runtime 实例

~~~text

    ↓

    ↓
追加 Agent 输出
~~~

3. 每个 SessionExecution 使用独立 Runtime 实例。
4. 以后需要进程重启恢复时，再增加序列化。

## 10. 阶段 5：收敛 SessionService 与 SessionExecution

### 新增文件

~~~text
code/agent/session/session_service.py
tests/session/test_session_execution.py
~~~

### 目标

将 Session 的创建与恢复收敛到一个应用服务：`SessionService` 创建持久化
Session 后立即打开它，已有 Session 也通过同一个打开流程恢复为
`SessionExecution`。运行中的共享 Context 与成员 Runtime 则由
SessionExecution 持有。

### 职责

- `SessionService.create_direct_session()` / `create_group_session()`：校验成员，
  原子创建持久化 Session 与固定成员，随后调用同一私有打开流程并返回
  SessionExecution。
- `SessionService.load(session_id)`：读取已有 Session 后调用同一私有打开流程。
- 私有打开流程：加载成员和稳定 Agent、创建唯一共享 Context、优先恢复
  `current_context_json`、创建 ContextService，并为每个成员装配独立 Runtime。
- 私有 Runtime 装配：为一个 Agent 成员创建其自己的 LLM、ExecutionContext、Tools
  和 PermissionManager。
- `SessionExecution`：处理 send、权限恢复、GROUP 顺序调度和 Context 持久化。

不再存在 `SessionCoordinator` 或 `SessionAgentRuntimeFactory`。两者都只是一次性
组装逻辑，没有独立业务规则；前者收敛到 SessionService，后者收敛为其私有
`_create_runtime()` 方法。

每个 Runtime 自己拥有该 Agent 的 ExecutionContext、Tools、PermissionManager 和
pending permission 状态。Runtime 只在调用时接收 SessionExecution 的共享 Context，
不保存 Context 属性，也不把 Agent Loop 移到 Session 层。

### Context 治理模型

Context 仍需要一个 LLM 用于压缩。SessionService 使用 Session 固定成员中的第一个
Agent 配置创建专用 summarizer LLM；该 LLM 仅属于该 Session 的 Context，不作为
任何 Agent Runtime 的模型实例。GROUP 因而只治理一次共享 Context，压缩规则和
结果对所有成员一致。

### SessionExecution

建议新增：

~~~python
class SessionExecution:
    session: Session
    context: Context
    context_service: ContextService
    members: tuple[SessionAgent, ...]
    runtimes: dict[str, Runtime]

    def send(self, message: str):
        ...

    def resolve_permission(self, response: PermissionResponse):
        ...
~~~

SessionExecution 是进程内的运行中会话状态，不等于持久化领域对象
`storage.types.Session`。它持有一个 Session Context，选择应运行的成员 Runtime，
并在每个 Runtime 事件边界保存 Context 快照；它不替代 Runtime 的 Agent Loop。

### DIRECT 流程

~~~text
SessionExecution.send(message)
    ↓
ContextService 保存用户事件
    ↓
Context.append_user_message(message)
    ↓
保存 current_context_json
    ↓
Runtime(primary).run(shared_context)
    ↓
Context 追加 Agent 消息和工具事件
    ↓
Context 治理
    ↓
保存 current_context_json，并将 Runtime 已产生的原始 Agent / 工具事件写入 ContextItem
~~~

### GROUP 流程

~~~text
SessionExecution.send(message)
    ↓
ContextService 保存用户事件并写入共享 Context
    ↓
Runtime(Agent1).run(shared_context)
    ↓
治理并保存 shared_context
    ↓
Runtime(Agent2).run(shared_context)
    ↓
Agent2 读取 Agent1 的最新消息和治理结果

GROUP 的顺序调度只负责“下一位成员是谁”。每一次成员处理仍由该成员的
`Runtime.run(context)` 完整执行；若 Runtime 产生权限请求，SessionExecution 记录
当前 Runtime 后暂停，`resolve_permission()` 只恢复该 Runtime，完成后才继续后续成员。

### 持久化规则

1. `send()` 先把用户消息作为原始 ContextItem 持久化，再写入共享 Context。
2. 每次 Runtime 产生事件后都保存 `current_context_json`，包括权限暂停处；它是下一次
   打开会话时实际恢复的模型上下文。
3. Runtime 已完成的 Agent 消息、function call 和 function call output 同步写入原始
   ContextItem 时间线，用于审计和没有快照时的初始恢复。
4. Context 快照与原始事件分工不同：前者允许被压缩覆盖，后者保留不可变业务时间线。
~~~

### 验收

- [x] SessionService 可创建和恢复 SessionExecution，且两条路径复用同一打开逻辑。
- [x] 一个 SessionExecution 只有一个 Context。
- [x] Agent 不拥有 Context。
- [x] ContextService 由 Session 创建和持有。
- [x] DIRECT 可以发送和恢复。
- [x] GROUP 可以按固定成员顺序调用多个独立 Runtime，并共享同一个 Context。
- [x] Runtime Loop 仍在 Runtime 内部。
- [x] 每个 Agent Runtime 独立拥有 Tools、ExecutionContext 和 PermissionManager。
- [x] 每轮完成和权限暂停时均保存 current_context_json。
- [x] 两个使用同一 Agent 的 Session 不共享 Context、Runtime 或权限状态。

### 实施记录

阶段 5 已完成，实际变更如下：

1. Session 创建和恢复均收敛到 `session/session_service.py`：`create_direct_session()`、
   `create_group_session()` 与 `load()` 都返回 SessionExecution，并复用 `_open()`。
2. 每个 SessionExecution 创建且只持有一个共享 Context。它优先恢复
   `current_context_json`，快照为空时才用原始 ContextItem 时间线恢复。
3. Context 使用固定成员中第一位 Agent 的独立 summarizer LLM；GROUP 的所有成员共享
   同一套压缩结果，但每个成员 Runtime 仍有各自的 LLM、Tools、ExecutionContext 和
   PermissionManager。
4. `send()` 先持久化用户业务事件，再更新共享 Context、保存快照，并调用当前成员
   `Runtime.run(context)`。GROUP 依固定成员顺序继续后续 Runtime。
5. `resolve_permission()` 恢复原先暂停的 Runtime 与同一个 Context；该成员完成后才会
   继续 GROUP 后续成员，避免丢失 Runtime 内部 pending 工具调用。
6. Runtime 已产生的 Agent 文本、function call、function call output 被同步为原始
   ContextItem；每个 Runtime 事件边界均覆盖保存治理后的 Context 快照。
7. 删除 SessionCoordinator 与 SessionAgentRuntimeFactory；Runtime 装配收敛为
   SessionService 私有 `_create_runtime()`，不再对外暴露无独立规则的 Factory。
8. 新增 SessionExecution 契约测试，覆盖治理快照恢复、原始时间线恢复、DIRECT 持久化、
   GROUP 共享 Context 和顺序调度、权限暂停/恢复，以及同一 Agent 跨 Session 隔离。

### 工作项

1. Session A 等待 call_A 权限时，Session B 的 call_B 不受影响。
2. call_A 的确认不能恢复 call_B。
3. 权限暂停前保存当前 Context。
4. 取消只停止当前 SessionExecution 中的当前 Runtime。
5. LLM 或工具失败后尽量保存已产生事件。
6. Web 层不暴露凭据、数据库路径和内部堆栈。

- [x] 原始事件和 current context 都保持有效。

### 实施记录

阶段 8 已完成，实际变更如下：

1. `Runtime.cancel()` 清除 pending 权限和未执行的工具队列，并使 Runtime 返回 IDLE；
   被取消的 call_id 不能再恢复。
2. `SessionExecution.cancel()` 只取消当前等待或正在执行的成员 Runtime，清除 Session
   内的等待成员标记，并覆盖保存已有的 Context 快照。GROUP 的后续成员不会因取消继续运行。
3. Session 调度每个成员的退出路径都在 `finally` 中同步 function call/function call output
   并保存 current context。因此 LLM 或工具在下一事件前异常时，已产生的协议事件和快照
   不会恢复为旧版本。
4. Web `ChatService.cancel()` 先调用原 `SessionExecution.cancel()`，再由 RunRegistry
   释放同 Session 的运行占用。RunRegistry 不承担 Runtime 控制职责。
5. 新增跨 Session Runtime 权限隔离测试：Session A 的 call_A 不能恢复 Session B 的
   call_B；原 Web run/callId 校验继续保证权限确认只对应当前 Run。
6. Web 运行异常继续输出稳定的 `RUN_FAILED` SSE 事件，测试确认不会泄露数据库路径、
   凭据字段或内部异常文本。

## 16. 事务和并发要求

原始事件和当前 Context 是两种不同数据：

~~~text
context_items
= 不可修改的原始业务事件

sessions.current_context_json
= 可以覆盖的当前模型上下文
~~~

首期保存边界：

1. 用户消息进入 Context 后。
2. Agent 消息完成后。
3. function call 追加后。
4. function call output 追加后。
5. Context 治理完成后。
6. 权限暂停前。
7. Agent Loop 完成、失败或取消后。

首期并发限制：

- 一个 Session 同时只有一个活动 Run。
- GROUP 内 Agent 串行执行。
- 一个 Context 同时只有一个写入者。
- 不允许两个 Runtime 同时修改同一个 Context。
