# 权限收缩与项目会话迭代计划

## 1. 目标

将权限从 Agent 的固有配置收缩为 Session 的运行约束。Agent 仅定义角色、LLM、指令与可用工具；一次 Session 决定工作目录、`plan/build/yolo` 模式和本会话的授权/拒绝规则。

> 术语收口：产品中的“项目目录”统一称为 Session 的“工作目录（workspace）”。它是 Agent 本轮执行实际使用的文件系统根目录，不要求目录必须是 Git 项目，也不代表数据库所在目录。数据库和历史领域代码中的 `project_path` 是当前迁移阶段保留的存储字段名，API 和 Web UI 使用 `workspacePath` / “工作目录”。

本计划替代此前“当前 Agent 权限模式”和“Agent 级权限规则”的产品语义。旧文档保留为历史实现记录，不再作为后续接口依据。

> 权限语义更新（2026-09-23）：原阶段 0-6 记录的是此前实现与收口过程。当前权限模式及工作目录外访问的权威规则以第 3 节和第 11 节为准；第 11 节是基于已完成权限收缩后的追加迭代，不回退 Agent/Session 的职责划分。

## 2. 最终产品形态

### 2.1 用户看到的内容

1. 新建或打开会话后，输入框左侧有工作目录按钮。用户可浏览、输入或不选择一个本机工作目录，直接开始普通对话。
2. 已选择目录时，输入区显示简洁的目录名或相对路径；目录选择按钮有可访问的提示文本。未选择时显示“未选择项目”。
3. Session 具有 `Plan`、`Build`、`YOLO` 三种模式。模式是会话设置，不属于 Agent；同一个 Agent 可同时参与不同模式的多个 Session。
4. 第一条用户消息成功写入 Session 后，工作目录永久锁定。界面显示锁定状态，不提供修改操作；避免工具历史、Session 授权和实际文件根目录发生错配。
5. 空工作区 Session 仍可完整进行 LLM 对话；任何需要工作目录的文件或终端工具都返回稳定的 `PROJECT_NOT_SELECTED` 工具结果，不回退到服务器当前工作目录。
6. 权限弹窗固定提供四个清晰操作：
   - `仅本次允许`：只执行当前 `call_id`。
   - `本会话允许`：对同一 Session 的后续同类请求自动允许。
   - `拒绝`：只拒绝当前 `call_id`。
   - `不再询问`：对同一 Session 的后续同类请求自动拒绝。
7. Session 允许/拒绝规则在重新打开 Session 或服务重启后仍有效；不同 Session 绝不互相影响。硬安全策略始终优先，`YOLO` 和“本会话允许”均不能绕过。

### 2.2 领域归属

```text
Agent
  角色、LLM、提示词、工具集合

Session
  项目目录、权限模式、Session 授权/拒绝规则、共享 Context

Runtime
  读取 Session 权限策略执行 Agent Loop；仅保存运行中的 pending 调用与队列
```

`PermissionManager` 是 Session 的共享策略对象，不是 Agent 成员。GROUP Session 中各 Runtime 复用同一个 Manager，因而同一会话的授权和拒绝判断一致；不同 Session 必须各自构造 Manager。

## 3. 明确的业务语义

### 3.1 权限模式

工作目录是默认访问范围，不是对所有模式都生效的不可突破沙箱。模式按以下规则决定默认访问；显式 Session 拒绝仍生效，强制黑名单始终优先且不能被授权覆盖：

| 模式 | 工作目录内读取 | 工作目录内写入 | 工作目录外文件/目录 | Bash / PowerShell |
| --- | --- | --- | --- | --- |
| `plan` | allow | deny | deny | 仅允许被可靠限制为工作目录内只读的命令；通用 Shell 默认拒绝 |
| `build` | allow | allow | ask | ask 每条命令 |
| `yolo` | allow | allow | allow | allow |

补充规则：

- `plan` 是只读模式：文件读取仅限工作目录；文件写入和工作目录外文件访问均拒绝，不弹确认。Bash/PowerShell 只有在执行器能够强制保证“只读且不能访问工作目录外”时才允许；通用 Shell 或无法证明安全的命令拒绝，不以命令字符串猜测其副作用。
- `build` 在工作目录内默认允许读取和写入；工作目录外的文件或目录读取、写入需要确认。通用终端命令每条整体确认，因为无法仅从命令文本可靠判断访问路径。用户可对确认请求选择仅本次或本会话授权。
- `yolo` 不受工作目录范围和普通受保护资源确认规则限制，文件工具与 Bash/PowerShell 均默认允许；只有 `HardSafetyPolicy` 的强制拒绝规则和用户显式 Session 拒绝仍然生效。
- 当前的 `ProtectedResourcePolicy` 属于额外确认策略，不等同强制黑名单：在 `plan/build` 下保留确认，在 `yolo` 下不再额外弹窗；强制黑名单不可覆盖。
- Session `allow` 只能放行本来可确认的请求，不能突破 `plan` 的只读/工作目录上限，也不能覆盖强制黑名单。Session `deny` 对该 Session 后续同范围请求持续拒绝。
- Bash/PowerShell 的权限请求没有单一文件资源。`plan` 只允许受限只读执行器能保证工作目录内只读的命令，通用 Shell 拒绝；`build` 每条命令整体确认；`yolo` 直接执行（强制黑名单除外）。选择“本会话允许/不再询问”会影响该 Session 后续所有终端命令，UI 必须明确提示。

`HardSafetyPolicy` 当前列出的硬拒绝包括关键系统认证文件写入和明确匹配的根目录递归删除命令。计划实施时必须把黑名单覆盖面及无法可靠静态识别的 Shell 绕过风险写入验收与风险项，不能将有限命令匹配描述成完整操作系统沙箱。

### 3.2 权限请求到协议字段的映射

保留现有 `PermissionResponse(call_id, decision, scope)` 形状，但收缩 scope 为 `once | session`：

| UI 操作 | `decision` | `scope` | 是否持久化 |
| --- | --- | --- | --- |
| 仅本次允许 | `allow` | `once` | 否 |
| 本会话允许 | `allow` | `session` | 是 |
| 拒绝 | `deny` | `once` | 否 |
| 不再询问 | `deny` | `session` | 是 |

`once` 不生成可复用规则，只作用于当前 pending 调用；`session` 规则按 `session_id + action + resource` 保存。对于 `bash.execute` 这类没有可可靠定位文件资源的动作，Session 规则覆盖该 Session 中同动作的后续终端调用；弹窗必须明确提示该影响范围。

### 3.3 工作目录与执行根

- Session 的工作目录就是用户为本次会话选择的 workspace；它可以是服务进程所在机器上的任意真实目录，不要求是 Git 项目。它为相对文件路径提供解析基准，并作为 `plan/build` 的默认授权范围。
- Web 目录选择器显示服务端解析后的完整路径，支持直接输入路径并通过“前往”或 Enter 导航。
- 目录 API 同时返回 `parentPath`。前端不自行拆分路径，因此 Windows 盘符、UNC 路径、macOS/Linux 绝对路径和文件系统根目录由服务端原生处理。
- Session 字段命名为 `project_path`，保存规范化绝对路径或 `NULL`；API 和 Web UI 使用 `workspacePath` / “工作目录”。
- `ExecutionContext` 使用 `project_path: str | None`，不再从 Agent 或状态数据库取得工作目录。没有工作目录时，文件工具和终端工具仍返回稳定的 `PROJECT_NOT_SELECTED`，普通 LLM 对话不受影响。
- 路径解析只负责把相对路径锚定到工作目录、规范化绝对路径并解析符号链接；它不能代替权限决策。`plan/build` 的边界由 `PermissionManager` 决定，`yolo` 可访问工作目录之外的路径。
- 权限检查和工具执行必须使用同一个规范化目标；确认后执行前要重新校验实际路径，防止符号链接变化或参数不一致导致执行目标偏离用户确认的资源。
- 项目目录必须存在且为目录。选择后至首条用户消息前可替换；第一条 `USER_MESSAGE` 与目录锁定校验要放在同一事务语义内，活动 Run 或已有用户消息时返回冲突错误。
- 当前 Web 由本机 FastAPI 服务托管，目录选择器通过服务端逐级浏览本机目录；UI 不提供任意路径文本输入。API 接受目录选择器返回的相对或绝对目录路径，只允许真实存在的目录，并跳过软链接目录。

## 4. 现状与要删除的内容

当前实现存在以下 Agent 级路径，均要删除，不保留兼容分支：

- `AgentProfile.permission_mode`、`Agent.permission_mode`、Agent 表单/API 的 `permissionMode`。
- `AgentFactory` 对 `PermissionMode(profile.permission_mode)` 的解析，以及 `workspace`、`PermissionRuleRepository` 注入到 Agent。
- `permission_agent_rules` 表和 `PermissionRuleRepository`，以及 `PermissionScope.AGENT`、`PermissionRequest.agent_id`、`PermissionRule.agent_id`。
- 前端 `PermissionScope = "agent"`、`ScopeSelector` 中“当前角色/该角色允许”。
- `PromptBuilder` 从 AgentProfile 推导权限模式的后备逻辑。

不能把既有 Agent 级 allow/deny 规则迁移到任意 Session：它们没有安全可信的 Session 归属。迁移时删除该表，旧规则不再生效。

### 阶段 2：收缩权限领域接口和纯策略

**目的**：从类型层禁止新的 Agent 级授权写入，并让策略明确以 Session 项目根为输入。

**改动**

1. 修改 `code/agent/permission/types.py`：
   - 删除 `PermissionScope.AGENT`。
   - 删除 `PermissionRequest.agent_id` 与 `PermissionRule.agent_id`。
   - `PermissionRule` 只允许 `SESSION` 身份；`PermissionResponse` 仍允许 `ONCE | SESSION`。
2. 修改 `PermissionManager` 构造器为 `mode`、`session_id`、`project_path`、`SessionPermissionRuleStore` 与硬策略依赖；不接受 Agent、Agent 仓储或数据库工作目录。
3. `PermissionManager.check()` 每次使用同一个 Session 规则集合，并按固定顺序判断：硬安全 -> 受保护资源 -> Session deny/allow -> 模式默认值。
4. `grant/deny()` 对 `once` 直接返回一次性处理结果，不写规则；对 `session` 先持久化成功再刷新内存规则，防止“数据库失败但本次运行认为已授权”。
5. 修改 `ModePolicy`：项目根为空时，文件/终端工具不由模式授权；项目外资源不因为 `yolo` 自动允许。保持硬安全和受保护目录优先。

### 阶段 4：定义并实现 Web API 契约

**目的**：让前端只通过 Session API 读写会话设置，且不再看见 Agent 权限字段。

**改动**

1. 修改 Agent schema、路由和映射：删除创建、更新、详情返回中的 `permission_mode` / `permissionMode`。
2. 扩展 Session DTO：`permissionMode`、`workspacePath`、`isWorkspaceLocked`。创建 DIRECT/GROUP 请求允许传入初始 `permissionMode`，默认 `plan`；`workspacePath` 必须经过服务端目录校验。
3. 新增 Session 设置接口：
   - `PATCH /api/sessions/{session_id}/permission-mode`，body 为受限模式枚举；活动 Run 时返回 `409`。
   - `PATCH /api/sessions/{session_id}/workspace`，body 为已验证的工作目录路径；首条用户消息后返回 `409 PROJECT_LOCKED`。
4. 新增工作目录浏览/选择接口。当前本机 Web 宿主允许从服务进程所在机器的目录树选择 workspace；接口返回当前完整路径、`parentPath` 和直接子目录元数据，隐藏目录和软链接不进入列表。
5. 修改运行确认 DTO：`scope` 只接受 `once | session`；服务端对 `PermissionResponse` 做强校验，不信任浏览器提供的 action/resource/session。
6. 更新 `ChatService`、`RunRegistry` 和 SSE 映射，保持 `runId + sessionId + callId` 的恢复校验不变。Session 设置变更成功后使对应 React Query 缓存失效。

## 9. 风险与约束

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 旧 Agent 规则无归属地迁移 | 误把某 Session 的权限扩散到其他 Session | 直接废弃旧规则，不做推测性迁移 |
| Session 中多个 Runtime 缓存规则不同步 | GROUP 对同一请求出现不同决定 | SessionExecution 只创建一个共享 Manager |
| 未选项目时回退进程目录 | 空项目对话意外拥有文件系统权限 | 工具显式返回 `PROJECT_NOT_SELECTED` |

| 运行中修改设置 | 同一 Run 前后权限边界不一致 | 活动 Run、pending permission 时 API 和 UI 都拒绝变更 |

## 10. 实施前需确认

本计划对以下语义采用默认结论；请在实现开始前确认第一项：

1. **目录选择宿主**：当前实现采用本机 FastAPI Web 服务，目录选择针对服务进程所在机器。后续若部署为远程服务，应改为桌面壳原生目录选择器或配置允许的根目录列表，不能让远程浏览器选择服务端任意目录。
2. **“不再询问”默认结论**：本计划定义为“当前 Session 内，对同一动作和资源范围持久化 deny”。这与“本会话允许”对称，不影响其他 Session。
3. **模式变更**：本计划允许 Session 空闲时随时切换 `plan/build/yolo`，并对下一次 Run 生效；活动 Run 和权限弹窗期间禁止切换。如需首轮后也锁定模式，应在阶段 1 一并加锁，而不是由前端单独限制。

- [x] 任意模式的强制黑名单不可被一次性或 Session allow 绕过；Session deny 可收紧权限。

#### 阶段 10：扩展 Session 权限规则存储到工作目录外

**为什么改**：当前仓储只把工作目录内路径编码为相对路径并拒绝外部资源。即使一次性确认可执行，“本会话允许/不再询问”也无法对工作目录外文件资源持久化。

**改动**

1. 修改 `code/agent/storage/repositories/session_permission_rule.py`：工作目录内资源继续用现有 `path` + 相对路径存储，工作目录外资源用新增的 `absolute_path` 类型保存规范绝对路径，不得把外部路径伪装成工作目录相对路径。
2. 当前表的 `resource_kind` / `resource_value` 没有受限枚举约束，增加 `absolute_path` 不需要数据库 schema migration；保持现有唯一键与旧 `path` 数据解释不变，并用旧数据回归测试验证。
3. `list_for_session()` 读取时校验路径格式，但不得仅因资源位于工作目录外就丢弃合法规则。
4. Session 规则的资源授权范围必须可展示、可审计，并遵循最小范围：文件读取的会话授权不应意外扩展到整个工作目录父级；目录读取的授权不应扩展到被选目录的父目录。
5. 即便数据库中已有旧 allow 规则，`plan` 外部路径上限及强制黑名单仍然先于 allow 生效。

**涉及文件**

- 修改：`code/agent/storage/repositories/session_permission_rule.py`、`code/agent/permission/PermissionManager.py`
- 修改：`tests/storage/test_session_permission_rule_repository.py`、`tests/test_permission_persistence.py`

**验收**

- [x] 已有 Session 规则保持原语义和资源目标，不跨 Session 泄漏；新增路径 kind 无需 schema migration。
- [x] 工作目录外 `FILE_READ/FILE_WRITE` Session 规则可保存、恢复和匹配。
- [x] 授权范围不超出用户确认的资源意图；`plan` 和强制黑名单上限不能被历史规则绕过。

### 11.4 风险与处理

| 风险 | 为什么重要 | 计划中的处理 |
| --- | --- | --- |
| 规范化目标和实际执行目标漂移 | 用户确认 A，工具却可能访问 B；并发替换路径仍可能造成 TOCTOU | 保存规范目标，执行前复核符号链接解析结果并向工具传递规范路径；这不是内核级无竞态隔离，若威胁模型要求对抗并发本机进程，后续需用目录句柄/安全文件打开 API 或 OS 沙箱 |
| `yolo` 被误解为完整安全沙箱 | 当前硬策略只识别有限命令和资源 | UI/文档明确风险；强制黑名单测试独立覆盖，不声称拦截所有 shell 等价命令 |
| Session allow 越权覆盖 plan | 持久化规则可能比当前模式更宽 | `plan` 上限先于 allow 规则，模式切换到 build/yolo 后再按相应规则判断 |
| Bash 会话授权影响范围过大 | Bash 请求没有可靠的文件资源 | build 每条命令确认；持久化 bash 规则按 session + action 管理并在 UI 说明覆盖所有后续命令 |
| 外部路径规则持久化错配 | 旧仓储使用 workspace-relative 编码 | 新增 `absolute_path` 编码，保留旧相对路径语义、唯一键与 Session 隔离，并以旧数据 fixture 验证 |
| plan 下“只读 Bash”无法由字符串检查保证 | shell 可执行脚本、重定向、子进程和任意程序 | 本期不新增受限执行器，通用 Bash/PowerShell 全部拒绝；未来只有在执行器能强制限制工作目录且具备只读能力后，才开放受限命令。不能只靠正则/命令名 allowlist 宣称具备沙箱隔离 |
