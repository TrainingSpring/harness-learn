# 数据持久化开发计划

## 计划目标

本计划按照《数据持久化方案》实现 Harness 的本地状态持久化，覆盖：

- 可复用的 LLM 配置。
- Agent 配置，包括描述、性格、擅长领域、指令和默认权限模式。
- Agent 可使用的工具集合；首期只持久化工具名称，不单独设计工具配置对象。
- Agent 范围权限规则。
- 会话、会话参与者和多 Agent 关系。
- 用户消息、Agent 消息、function call、function call output 等上下文。
- Agent 委托链、群聊和 Agent 自主对话所需要的消息目标与可见性。

第一阶段只实现本地 SQLite 和 CLI 可验证闭环，不提前实现 Web UI、云同步、跨 workspace 全局配置和附件二进制存储。

## 当前代码基础

当前代码已经具备以下能力：

- Agent 直接组装 LLM、Tools、Context、Runtime 和 PermissionManager。
- Tools.register_by_names() 根据工具名称动态导入 tools.<name> 模块。
- 工具统一返回 ToolResult。
- Runtime 已经可以处理 function call、工具执行、权限暂停和恢复。
- PermissionManager 已经支持 ONCE、SESSION、AGENT 三种权限范围。
- Context 主要是内存中的 Responses 请求上下文。

本次工作不是重新实现 Agent loop，而是增加持久化边界，并把现有 Runtime 改造成能够读写持久状态的运行时。

## 总体依赖顺序

~~~text
领域模型与接口契约
        ↓
SQLite、迁移和基础仓储
        ↓
LLMProfile / AgentProfile / Tool 集合加载
        ↓
AgentFactory 组装运行时 Agent
        ↓
权限规则迁入统一状态库
        ↓
Session / Participant / ContextItem
        ↓
单 Agent 会话恢复
        ↓
委托、群聊和 Agent 间消息
        ↓
OPEN 模式、CLI 选择和恢复体验
~~~

数据库、领域模型和接口必须先确定，再修改 Agent 与 Runtime。否则容易把 SQL 逻辑直接塞进 Agent，最终形成一个同时负责配置、会话、权限和 LLM 调用的巨型对象。

storage/types.py 新增以下领域对象：

~~~text

~~~

每个类型都需要中文类注释、属性注释和构造参数注释，至少说明：

- 所有持久化 ID 都是带前缀的随机字符串，不使用纯数字自增 ID。
- agent_id 是 Agent 的稳定身份；name 只是展示名称。
- AgentProfile 是可持久化配置，Agent 是运行时对象。
- Session 不保存单个 Agent 外键。
- SessionParticipant 是某个 Agent 在某个会话中的参与身份。
- ContextItem 的 visibility 和单个目标如何共同决定可见性。
- caused_by_item_id 是事件因果关系，不是消息目标。

推荐字段如下：

~~~text
LLMProfile:
  id, name, provider, base_url, model, api_key,
  options, created_at, updated_at

AgentProfile:
  id, name, description, personality, expertise,
  llm_profile_id, tools, permission_mode,
  is_enabled, created_at, updated_at

Session:
  id, title, conversation_mode, status,
  created_at, updated_at, closed_at

SessionParticipant:
  id, session_id, agent_profile_id, role, join_reason,
  joined_at, left_at

ContextItem:
  id, session_id, sequence_no, kind, author_participant_id,
  target_participant_id, visibility, call_id,
  caused_by_item_id, payload, created_at

AgentDelegation:
  id, session_id, requester_participant_id, worker_participant_id,
  request_item_id, parent_delegation_id, status,
  result_item_id, created_at, completed_at
~~~

storage/errors.py 新增稳定的存储错误类型：

- StorageError：存储层错误基类。
- StorageSchemaError：schema 版本异常或迁移失败。
- StorageFormatError：数据库字段或 JSON 结构非法。
- StorageConflictError：唯一约束、并发更新或状态冲突。

这样上层可以区分数据库损坏、用户配置错误和运行时工具失败，不会把所有错误都包装成普通字符串。

为什么先做这一层：后续 Repository、ContextService 和 OrchestrationService 都依赖这些类型。如果直接用 dict 传递，会重新出现字段名不一致、Agent 身份标识混用以及不同模块返回不同结构的问题。

### 定义 Repository 接口

在 storage/types.py 或新增 storage/protocols.py 中定义 Repository 接口。首期可以使用 Protocol，但不要求立即实现多个数据库后端。

必须先固定以下接口语义：

~~~text
LLMProfileRepository
  get(profile_id)
  get_by_name(name)
  list_all(limit, offset)
  save(profile)
  delete(profile_id)

AgentProfileRepository
  get(agent_id)
  list_enabled(limit, offset, expertise=None)
  save(profile)
  delete(agent_id)

SessionRepository
  create(mode, title=None)
  get(session_id)
  update_status(session_id, status)
  list_recent(limit, offset)

SessionParticipantRepository
  add(participant)
  get(participant_id)
  list_active(session_id)
  find(session_id, agent_profile_id)

ContextItemRepository
  append(item)
  list_after(session_id, sequence_no)
  list_visible(session_id, participant_id)
  find_by_call_id(session_id, call_id)

AgentDelegationRepository
  create(delegation)
  update_status(delegation_id, status, result_item_id=None)
  get(delegation_id)
  list_for_session(session_id, status=None)
~~~

接口必须明确：

- append 是追加操作，不允许修改历史上下文项。
- sequence_no 由仓储在事务中生成，不能由上层用当前列表长度猜测。
- list_visible 必须执行可见性过滤，调用方不能拿全量历史后自行筛选。
- Repository 返回领域对象，不返回 SQLite Row 或裸字典。

验收标准：类型、状态枚举、字段命名和接口返回值已固定；每个接口都有对应测试用例或待实现测试说明。

### 统一 ID 生成规则

新增文件：

~~~text
code/agent/storage/ids.py
tests/storage/test_ids.py
~~~

所有持久化实体使用 TEXT 类型的“语义前缀 + 随机字符串”作为 ID，不使用纯数字自增主键。例如：

~~~text
agent_1V3ASAXQ2A
llm_7KQ2M8P4XZ
session_4N9C1R7WBA
participant_8T2LQ6MZP1
item_3F7XK9A2VC
delegation_5H1R8DQP6M
~~~

新增统一生成函数，例如：

~~~python
generate_id("agent") -> "agent_1V3ASAXQ2A"
~~~

要求：

- 前缀由实体类型决定，便于日志、迁移和排查问题。
- 随机部分不包含时间序号，不暴露创建数量和创建顺序。
- 数据库仍然对 ID 建立 PRIMARY KEY 或 UNIQUE 约束。
- 迁移、导入和导出时原 ID 保持不变，不重新按数据库行号生成。
- Repository 不允许把 ID 转换成整数。

AgentProfile 的 id 在业务层命名为 agent_id。SessionParticipant 保存 agent_id 外键；权限规则也使用 agent_id。当前代码中的 agent_key 需要在迁移阶段统一替换或作为兼容字段逐步废弃。

**为什么这样做**：自增整数只在单个数据库中稳定，数据合并、导入导出或多 workspace 迁移时容易发生冲突。带前缀的随机 ID 可以直接跨数据库搬运，且从 ID 本身能看出它对应的实体类型。

## SQLite 基础层与 Schema 迁移

### 新增数据库生命周期管理

新增文件：

~~~text
code/agent/storage/database.py
code/agent/storage/migrations.py
~~~

新增 StateDatabase，职责包括：

- 根据 workspace 计算 workspace/.harness/state.db。
- 首次写入时创建 .harness。
- 打开 SQLite 连接并启用 PRAGMA foreign_keys = ON。
- 设置合理的 busy timeout。
- 初始化和升级 schema。
- 提供事务上下文管理。
- 在宿主退出时关闭连接。

StateDatabase 不允许负责：

- 判断权限是否允许。
- 创建 Agent。
- 调用 LLM 或工具。
- 把数据库行直接暴露给 Runtime。

迁移必须使用显式版本号：

~~~text
schema_metadata.schema_version = 1
~~~

首个版本建立以下表：

~~~text
schema_metadata
llm_profiles
agent_profiles
permission_agent_rules
sessions
session_participants
context_items
agent_delegations
~~~

artifacts 暂不建立，等图片、音频和文件附件真正进入持久化闭环后再增加迁移。

为什么使用一个数据库：权限、Agent 配置和会话之间存在外键及事务关系。分散为多个 JSON 或多个数据库会产生孤立权限规则、会话参与者无法恢复等问题。

### 完成 Schema 约束和索引

需要实现的约束：

- llm_profiles.name 唯一。
- agent_profiles.id 使用 agent_ 前缀的随机字符串。
- session_participants(session_id, agent_id) 唯一。
- context_items(session_id, sequence_no) 唯一。
- 所有主键和外键使用对应实体的带前缀字符串 ID。
- 所有外键启用级联策略或由 Repository 显式控制删除顺序。
- permission_agent_rules 保留既有权限规则的唯一槽位约束。

需要增加的索引：

~~~text
context_items(session_id, sequence_no)
context_items(session_id, call_id)
session_participants(session_id, left_at)
agent_delegations(session_id, status)
~~~

payload_json 和 options_json 必须使用参数绑定写入，禁止 SQL 字符串拼接。

验收标准：空 workspace 可以创建数据库；重复初始化不会破坏数据；外键、唯一约束和 schema 版本检查均有测试；schema 版本高于当前程序时启动失败并提示升级。

新增 PromptBuilder，在运行时根据 AgentProfile 和当前环境组装 LLM 指令：


组装内容包括：

### 实现权限规则 Repository

从现有《权限规则持久化方案》迁入实现：

- 只持久化 PermissionScope.AGENT。

- SESSION 只保存在当前会话运行时内存，恢复会话时不自动恢复。

- 数据损坏采取失败关闭，不能静默跳过非法规则。

### 修改 PermissionManager 的依赖和写入顺序

修改文件：

~~~text
code/agent/permission/PermissionManager.py
~~~

- 构造时注入稳定的 agent_id 和 PermissionRuleRepository。

### 修改 Runtime 的事件写入点

修改文件：

~~~text

~~~

当前 Runtime 直接调用 context.append_msg()，需要改成由 ContextService 统一记录：

~~~text
run(message)
  -> append USER_MESSAGE

收到 LLM message
  -> append AGENT_MESSAGE

收到 function_call
  -> append FUNCTION_CALL
  -> 进入权限预检和工具队列

工具执行完成
  -> append FUNCTION_CALL_OUTPUT
~~~

需要特别处理 function call 与 output 之间的异常：

- function call 已持久化但进程中断时，恢复逻辑必须识别未完成调用。
- 不能伪造成功的 function call output。
- 首期可以将其标记为未完成，并在恢复时生成稳定失败结果，具体策略通过测试固定。
- 权限等待期间，pending 调用的 function call 已保存，但 output 必须等用户确认并执行后再保存。

Runtime 仍然负责 LLM loop、权限暂停和工具执行；它不负责 SQL、序号生成和目标可见性判断。

### 实现三种上下文投影

ContextService.load_visible_context(session_id, participant_id) 按以下顺序处理：

~~~text
读取 SessionParticipant 状态
  -> 读取 PUBLIC 项
  -> 读取 target_participant_id 等于该 participant 的 TARGETED 项
  -> 读取该 participant 自己的 PRIVATE 项
  -> 读取委托任务明确允许共享的上下文
  -> 按 sequence_no 排序
  -> 应用上下文窗口截断或摘要
  -> PromptBuilder 根据 AgentProfile 组装运行时 instructions
  -> 编码为 LLM provider 请求
~~~

三种模式的默认投递规则：

~~~text
DIRECT:
  用户消息 -> PRIMARY Agent
  委托请求 -> 被委托 Agent
  委托结果 -> 请求 Agent

GROUP:
  用户消息 -> 所有活跃 Agent
  Agent 发言 -> 默认 PUBLIC

OPEN:
  Agent 消息 -> 按策略 PUBLIC 或 TARGETED
  OrchestrationService 控制轮数、预算和停止条件
~~~

这些只是默认规则。目标和可见性仍然需要通过统一服务创建，不能由 UI 直接拼接数据库行。

## 数据读取、删除与恢复

### 实现读取接口

所有 Repository 的列表读取都要考虑 UI 和未来数据量：

- list_recent() 支持 limit 与 offset。
- 上下文读取支持按 session_id 和 sequence_no 增量读取。
- Agent 列表支持按启用状态和 expertise 过滤。
- 委托列表支持按状态过滤。
- 权限规则支持按 Agent 查询。

不使用“读取全部历史再在 Python 中过滤”的方式，避免会话变大后内存和模型上下文一起膨胀。

### 实现删除语义

首期至少实现 Repository 层的显式删除，并明确外键顺序：

~~~text
删除 Session
  -> 删除 AgentDelegation
  -> 删除 ContextItem
  -> 删除 SessionParticipant
  -> 删除 Session
~~~

删除 AgentProfile 前检查：

- 是否被 SessionParticipant 引用。
- 是否有 AGENT 权限规则。
- 是否仍被其他配置引用。

首期不自动删除历史会话或权限规则。CLI/UI 未来提供显式删除并要求确认。

### 定义异常恢复行为

需要覆盖：

- LLM 输出 function call 后进程中断。
- 工具执行完成但 output 尚未持久化。
- 权限等待期间进程退出。
- Agent 委托建立后 worker 尚未启动。
- OPEN 模式达到轮数或预算上限。

恢复不能把未完成状态伪装成成功。应通过 SYSTEM_EVENT 或稳定的失败 FUNCTION_CALL_OUTPUT 表达状态，并在实现阶段选择一种统一策略。

## 风险与处理方式

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 把 Agent 配置和 Agent 运行时对象混在一起 | Agent 无法复用，重启恢复困难 | 使用 AgentProfile + AgentFactory 分离 |
| Session 绑定单个 Agent | 无法表达委托和群聊 | 使用 SessionParticipant 多对多关系 |
| ContextItem 只有单个目标 | 暂不支持向指定的多个 Agent 定向发送 | 首期使用 PUBLIC 或单个 target_participant_id；未来确有需求时再增加目标关联表 |
| 新 Agent 自动读取全部历史 | 可能泄露私有上下文 | 加入时间、目标过滤和显式共享引用 |
| 数据库保存 API Key | 凭据泄露 | 限制 workspace 文件权限；日志、异常、列表、普通详情和导出配置不返回明文，编辑专用接口仅供本地 UI 回显 |
| Tool 配置加载任意模块 | 可执行不受信任代码 | 工具函数只能来自代码 ToolCatalog |
| OPEN 模式无限对话 | 资源和费用不可控 | 最大轮数、token/消息预算、空转检测 |
| Runtime 直接写 SQL | 运行逻辑与存储强耦合 | ContextService 和 Repository 隔离 |
| function call 与 output 中断 | 恢复时上下文不一致 | 保存调用状态，统一处理未完成调用 |
| 过早实现附件和摘要 | 增加没有消费者的复杂度 | 先完成文本和结构化结果，附件后置 |
