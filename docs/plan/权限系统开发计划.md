# 权限系统开发计划

## 1. 计划目标

本计划把 [权限系统开发方案](../权限系统开发方案.md) 拆成可逐步提交、可独立验证的改动。首版只支持内存规则、CLI 确认和现有四个本地工具：`read`、`write`、`edit`、`bash`。

本计划的完成标准：

1. 每个工具调用在执行前都得到 `allow`、`deny` 或 `ask` 的明确决策。
2. `ask` 不执行工具、不调用下一轮 LLM，而是向 CLI 暴露待确认请求。
3. 用户确认后，Runtime 能从原调用的 `call_id` 恢复，并将标准的 `function_call_output` 写回上下文。
4. 用户可为一次调用、当前会话、当前逻辑 Agent 写入允许或拒绝规则。
5. `plan/build/yolo` 只提供默认策略，不能覆盖绝对黑名单或受保护资源策略。
6. 现有 `ToolResult -> Responses output` 编码契约保持不变。

## 2. 现状与改动边界

当前主要调用链是：

```text
Agent.send()
  -> Runtime.run()
     -> LLM 返回 function_call
     -> Runtime 直接调用 PermissionManager.check(...)
     -> Tools.eval(...)
     -> Context 追加 function_call_output
```

现状有三个必须先解决的问题：

- `PermissionManager.check()` 尚未实现，且参数是静态 `Permission` 与原始 arguments，无法表达一次实际调用的 `call_id/session/agent/resource`。
- `Runtime.run()` 将 `check()` 当成“成功或抛异常”的同步前置校验，无法暂停到用户确认后再恢复。
- `Tools.eval()` 自行解析 arguments；权限检查也需要相同的已解析参数，若不调整会形成重复解析和不一致的错误处理。

本次不修改各工具内部的文件读写实现，也不把 workspace 边界、软链接解析、进程隔离做进本期。它们仍属于后续 harness 安全层。

## 4. 阶段一：先建立权限领域类型

### 4.1 新增 `code/agent/permission/types.py`

新增以下类型，全部使用 `dataclass(frozen=True)` 或 `StrEnum`。使用值对象而非裸字符串和字典，是为了让工具、Runtime、策略和 CLI 使用同一套字段，避免在多个文件中隐式约定参数名。

```python
class PermissionAction(StrEnum):
    FILE_READ = "filesystem.read"
    FILE_WRITE = "filesystem.write"
    BASH_EXECUTE = "bash.execute"


class PermissionDecision(StrEnum):
    ALLOW = "allow"
    DENY = "deny"
    ASK = "ask"


class PermissionScope(StrEnum):
    ONCE = "once"
    SESSION = "session"
    AGENT = "agent"


class PermissionMode(StrEnum):
    PLAN = "plan"
    BUILD = "build"
    YOLO = "yolo"


@dataclass(frozen=True)
class PermissionRequirement:
    action: PermissionAction
    resource_from: str | None


@dataclass(frozen=True)
class PermissionRequest:
    action: PermissionAction
    resource: str | None
    tool_name: str
    call_id: str
    session_id: str
    agent_key: str


@dataclass(frozen=True)
class PermissionRule:
    action: PermissionAction
    resource: str | None
    decision: PermissionDecision
    scope: PermissionScope
    call_id: str | None = None
    session_id: str | None = None
    agent_key: str | None = None
```

还需新增 `PermissionResponse`，作为 CLI 传给 Runtime 的确认输入：

```python
@dataclass(frozen=True)
class PermissionResponse:
    call_id: str
    decision: PermissionDecision  # 只允许 ALLOW / DENY
    scope: PermissionScope
```

`PermissionResponse` 不携带 action、resource、session 或 agent 字段。Runtime 必须从已保存的 `PendingToolCall.request` 取得这些值，避免 CLI 或未来的 UI 把确认写到错误资源或错误 Agent。

类型构造约束：

- `PermissionRule.decision` 不允许 `ASK`；`ASK` 是瞬时决策，不是可写入规则。
- `ONCE` 规则必须只有 `call_id`，`SESSION` 必须只有 `session_id`，`AGENT` 必须只有 `agent_key`。非法组合在 `__post_init__()` 立即报错。
- 有资源的规则必须是规范化绝对路径；`resource=None` 只允许 `bash.execute` 等无可靠资源归属的动作。

这些约束应在模型创建处完成，而不是在所有匹配逻辑中重复判断。

### 4.2 新增 `code/agent/permission/__init__.py`

只导出供外部模块使用的类型和 `PermissionManager`，例如：

```python
from .PermissionManager import PermissionManager
from .types import PermissionAction, PermissionDecision, PermissionMode
from .types import PermissionRequirement, PermissionRequest, PermissionResponse, PermissionScope
```

原因是外部模块不再依赖 `PermissionManager.py` 的内部布局。将来增加持久化实现或重排文件时，`tools`、`runtime` 和 CLI 的 import 不需要重写。

### 4.3 修改 `code/agent/permission/PermissionManager.py`

本文件删除现有 `Permission`、`PermissionAction`、`PermissionType` 和 `_args_str_to_dict()`：

- `Permission` 改由 `PermissionRequirement` 替代，避免和“已授权的 PermissionRule”混淆。
- `PermissionAction` 与决策枚举移到 `types.py`，防止工具模块为了类型而依赖 Manager 实现。
- 参数 JSON 解析移出 Manager。Manager 的边界输入必须是已经构造好的 `PermissionRequest`。

初始构造器改为：

```python
def __init__(
    self,
    mode: PermissionMode,
    hard_safety_policy: HardSafetyPolicy | None = None,
    protected_resource_policy: ProtectedResourcePolicy | None = None,
) -> None:
```

实例字段：

- `_mode`：当前 Agent 的默认权限模式。
- `_rules: list[PermissionRule]`：首版内存规则表。
- `_hard_safety_policy`、`_protected_resource_policy`：不变策略对象。

此处不要把 `ExecutionContext` 注入 Manager。Manager 的每次判断都从 `PermissionRequest` 获得运行身份；这样 Manager 可脱离 Agent、LLM 和文件系统做纯单元测试。

### 4.4 修改 `code/agent/session/ExecutionContext.py`

将当前 `aid`/未初始化的 `sid` 替换为明确字段：

```python
@dataclass(frozen=True)
class ExecutionContext:
    workspace: str
    agent_key: str
    session_id: str
    max_tool_call_length: int = 20_000
```

`agent_key` 表示可跨会话稳定识别的逻辑 Agent，例如 `code_editor`；`session_id` 是本次交互会话的随机标识。不要把当前随机实例 ID 用作 Agent 授权键，否则“当前 Agent 允许”会在重启后失效，语义退化为 session。

### 4.5 修改 `code/agent/runtime/agent.py`

调整 `Agent.__init__()`：

```python
def __init__(
    self,
    llm_config: LLMConfig,
    tools: list[str],
    context: Context | None = None,
    agent_key: str = "default",
    permission_mode: PermissionMode = PermissionMode.BUILD,
    workspace: str | None = None,
) -> None:
```

具体改动：

- `workspace` 缺省时仍使用 `os.getcwd()`；显式参数只改善测试和未来多 Agent 配置，并不实现路径隔离。
- 每个 Agent 创建一个 `session_id`，并用 `workspace/agent_key/session_id` 建立 `ExecutionContext`。
- 用 `PermissionManager(permission_mode)` 创建权限管理器。
- 新增 `Agent.resolve_permission(response: PermissionResponse)`，只代理 `Runtime.resolve_permission()`；CLI 不接触 Runtime 内部字段。

原因：`Agent` 是组装根，负责把稳定配置和本次执行身份交给下层；`Tools` 和工具函数只收到不可变的 `ExecutionContext`。

阶段一验收：所有原有导入迁移到新类型文件；`pytest` 能导入整个项目；此阶段不改变实际 allow/deny 行为。

## 5. 阶段二：实现纯策略与规则决策

### 5.1 新增 `code/agent/permission/policies.py`

该文件只放无状态、可单测的策略。不要引入可动态注册的 policy 插件系统，首版只需要三个明确职责。

#### `HardSafetyPolicy`

```python
class HardSafetyPolicy:
    def check(self, request: PermissionRequest) -> PermissionDecision | None:
        ...
```

命中返回 `DENY`，不命中返回 `None`。首版只实现经过明确确认的极危险模式，例如对系统关键资源的破坏性写入和少量不可接受的命令结构。不要宣称可完整解析 shell；`bash` 的 `resource=None` 不允许用猜测出的路径取代真实资源。

`HardSafetyPolicy` 可以额外接受 `command: str | None`，但该值只能来自 `PreparedToolCall.arguments["command"]`，仅用于有限的黑名单匹配。它必须在 `PermissionRequest` 之外显式传入，避免把原始工具参数混入长期存储的规则对象。

#### `ProtectedResourcePolicy`

```python
class ProtectedResourcePolicy:
    def requires_confirmation(self, request: PermissionRequest) -> bool:
        ...
```

首版构造器接收规范化的受保护目录列表，例如系统目录和 Agent 配置目录。命中时，读写均返回 `ASK`；此策略不关心规则和模式。

#### `ModePolicy`

```python
class ModePolicy:
    def decide(self, mode: PermissionMode, request: PermissionRequest) -> PermissionDecision:
        ...
```

固定默认表：

| 模式 | 文件读 | 文件写 | bash | 项目外普通资源 |
| --- | --- | --- | --- | --- |
| `PLAN` | allow | deny | deny | deny |
| `BUILD` | allow | ask | ask | ask |
| `YOLO` | allow | allow | allow | allow |

“项目外”判定通过 `request.resource` 与 `ExecutionContext.workspace` 的规范化路径边界比较完成。为保持 Policy 无 Agent 依赖，应把 `workspace` 作为构造参数传给 `ModePolicy`，而不是把整个 Context 传入 `check()`。

### 5.2 在 `PermissionManager.py` 新增规则操作

新增公开方法：

```python
def check(
    self,
    request: PermissionRequest,
    *,
    command: str | None = None,
) -> PermissionDecision:
    ...

def grant(
    self,
    request: PermissionRequest,
    scope: PermissionScope,
    resource: str | None,
) -> PermissionRule:
    ...

def deny(
    self,
    request: PermissionRequest,
    scope: PermissionScope,
    resource: str | None,
) -> PermissionRule:
    ...
```

新增私有方法：

```python
def _find_matching_rule(self, request: PermissionRequest) -> PermissionRule | None: ...
def _rule_matches(self, rule: PermissionRule, request: PermissionRequest) -> bool: ...
def _resource_matches(self, rule_resource: str | None, request_resource: str | None) -> bool: ...
def _scope_matches(self, rule: PermissionRule, request: PermissionRequest) -> bool: ...
def _replace_rule(self, rule: PermissionRule) -> None: ...
```

`grant()` / `deny()` 必须由 `request` 自动填充 `call_id/session_id/agent_key`，调用方只能传 `scope` 和确认后的资源范围。这样可避免 CLI 或未来 HTTP 层伪造主体字段。

资源范围计算不放在 `PermissionManager`：Runtime 在确认时调用一个由 `Tools` 提供的 `default_grant_resource(request)`。文件请求默认返回目标的父目录，`bash` 返回 `None`。Manager 只验证该资源已规范化并写入规则。

### 5.3 固定 `check()` 的判断顺序

实现必须严格按以下顺序返回，不允许由调用方自行拼装：

```text
1. HardSafetyPolicy 命中                    -> DENY
2. ProtectedResourcePolicy 命中              -> ASK
3. 已命中的规则（DENY 或 ALLOW）              -> 规则决定
4. ModePolicy 默认策略                       -> ALLOW / DENY / ASK
```

规则内部排序：

1. `ONCE` 优先于 `SESSION`，优先于 `AGENT`。
2. 同一 scope 中，路径更深的规则优先。
3. scope 和路径深度相同，最新写入的规则替换旧规则，而不是依赖 list 遍历顺序。

这一排序保证“本次特殊允许”能压过较宽的 Agent 规则，同时“允许 `src/`、拒绝 `src/.env`”可预测地工作。

阶段二验收：无需 LLM、CLI 或真实工具，表驱动单测可验证每一个决策分支。

## 6. 阶段三：调整工具调用边界

### 6.1 修改 `code/agent/tools/types.py`

将 `Tool.permission` 的类型从旧 `Permission` 改为 `PermissionRequirement`。

新增：

```python
@dataclass(frozen=True)
class PreparedToolCall:
    call_id: str
    tool_name: str
    tool: Tool
    arguments: dict[str, Any]
    permission_request: PermissionRequest


class ToolCallPreparationError(Exception):
    def __init__(self, error: ToolError) -> None: ...
```

`PreparedToolCall` 是“已找到工具、已解析参数、已构造权限请求”的唯一传递对象。它避免 Runtime 以 `item.name/item.arguments/item.call_id` 三个松散字段调用不同 API，也避免 `Tools.eval()` 重复 JSON 解析。

`ToolCallPreparationError` 只用于 `Tools -> Runtime` 的内部边界，携带 `ToolError`。Runtime 捕获后立即转为 `ToolResult.failure`。因此模型仍然只看到统一的工具结果格式，异常不会成为公共协议。

### 6.2 修改 `code/agent/tools/tools.py`

保留注册和 Responses 编码逻辑，新增和调整如下：

```python
def prepare_call(
    self,
    name: str,
    arguments: str | dict | None,
    call_id: str,
) -> PreparedToolCall:
    ...

def build_permission_request(
    self,
    tool: Tool,
    tool_name: str,
    arguments: dict[str, Any],
    call_id: str,
) -> PermissionRequest:
    ...

def execute(self, call: PreparedToolCall) -> ToolResult:
    ...

def encode_result(self, result: ToolResult) -> str | list[dict]:
    ...

def default_grant_resource(self, request: PermissionRequest) -> str | None:
    ...
```

具体职责：

- `prepare_call()` 查找 Tool、解析 JSON、确保参数为 `dict`，缺失工具或参数非法时抛出 `ToolCallPreparationError`。
- `build_permission_request()` 根据 `tool.permission.resource_from` 取得资源参数。文件资源用 `handle_path()`、`os.path.abspath()`、`os.path.normpath()` 规范化；缺失资源参数属于 `INVALID_ARGUMENTS`。`resource_from=None` 时，资源为 `None`。
- `execute()` 只调用 `tool.function(ctx, **arguments)` 并将异常、非 `ToolResult` 返回统一为 `ToolResult.failure`。它不再做 JSON 解析，也不检查权限。
- 将现有 `_encode_output()` 重命名为公开 `encode_result()`；Runtime 需要对权限拒绝产生的 `ToolResult` 走同一编码器，不能调用带下划线的私有方法。
- `default_grant_resource()` 对文件操作返回 `dirname(request.resource)`；对资源为 `None` 的 `bash` 返回 `None`。它只决定 CLI 默认授权范围，不判断是否安全。

旧 `eval()` 在本阶段删除，并同步更新唯一调用方 `Runtime`。CodeGraph 显示当前只有 Runtime 调用它，因此可以进行一次原子迁移；测试中若有直接调用，也一并迁移到 `prepare_call + execute + encode_result`。

### 6.3 修改四个工具的权限声明

| 文件 | 现有声明 | 目标声明 | 原因 |
| --- | --- | --- | --- |
| `tools/read.py` | `Permission(file_read, "target_path")` | `PermissionRequirement(FILE_READ, "target_path")` | 文件或目录读取需要实际路径。 |
| `tools/write.py` | `Permission(file_write, "target_path")` | `PermissionRequirement(FILE_WRITE, "target_path")` | 写文件及创建父目录属于写权限。 |
| `tools/edit.py` | `Permission(file_write, "target_path")` | `PermissionRequirement(FILE_WRITE, "target_path")` | 虽然内部先读后写，外部动作按最终副作用分类。 |
| `tools/bash.py` | `Permission(bash_execute, "command")` | `PermissionRequirement(BASH_EXECUTE, None)` | 命令文本不是可可靠匹配的资源路径；首版按命令执行动作授权。 |

工具函数签名保持 `tool(ctx, ...) -> ToolResult` 不变。工具不接收 `PermissionManager`、`PermissionRequest` 或用户选择；这样工具不承担策略职责，也能继续独立测试。

阶段三验收：一份 function call 的 arguments 只解析一次；资源路径能被正确规范化；所有工具仍只返回 `ToolResult`。

## 7. 阶段四：实现 Runtime 的暂停、队列和恢复

### 7.1 修改 `code/agent/runtime/runtime.py` 的状态对象

新增：

```python
class RuntimeState(StrEnum):
    IDLE = "idle"
    RUNNING = "running"
    WAITING_PERMISSION = "waiting_permission"


@dataclass
class PendingToolCall:
    call: PreparedToolCall
    command: str | None


@dataclass(frozen=True)
class PermissionRequiredEvent:
    type: Literal["permission_required"]
    request: PermissionRequest
    available_scopes: tuple[PermissionScope, ...]
```

Runtime 新增实例字段：

- `_state: RuntimeState`，初始为 `IDLE`。
- `_pending_permission: PendingToolCall | None`，当前等待用户确认的一个调用。
- `_tool_queue: deque[PreparedToolCall]`，保存同一 LLM 轮次中尚未处理的多个 function call。

使用队列是必要的。Responses 一次完成事件可能包含多个 function call；遇到第一个 `ASK` 后不能继续执行后续调用，也不能丢弃它们。队列会在恢复后按模型给出的顺序继续处理。

### 7.2 重构 `Runtime.run()`

将大循环拆成以下私有方法：

```python
def run(self, message: str) -> Generator[LLMEvent | PermissionRequiredEvent, None, None]: ...
def _run_llm_loop(self) -> Generator[LLMEvent | PermissionRequiredEvent, None, None]: ...
def _enqueue_function_calls(self, output_items: list[LLMResponseOutputItem]) -> None: ...
def _drain_tool_queue(self) -> PermissionRequiredEvent | None: ...
def _handle_prepared_call(self, call: PreparedToolCall) -> PermissionRequiredEvent | None: ...
def _append_tool_result(self, call_id: str, result: ToolResult) -> None: ...
def _permission_denied_result(self, request: PermissionRequest) -> ToolResult: ...
```

详细流程：

1. `run(message)` 仅在 `IDLE` 时允许调用，追加 user message 后置为 `RUNNING`。
2. `_run_llm_loop()` 调用 LLM。收到完整输出后，保持当前行为先把 message/function_call 原样追加到 `Context`。
3. 对每个 function call 调用 `tools.prepare_call()` 并放入 `_tool_queue`。准备失败时立即将对应 `ToolResult.failure` 追加为 output，不进入权限流程。
4. `_drain_tool_queue()` 顺序处理队列：调用 `permission.check(request, command=...)`。
5. `ALLOW`：`tools.execute(call)`，再 `_append_tool_result()`。
6. `DENY`：生成 `ToolResult.failure("PERMISSION_DENIED", ...)`，再 `_append_tool_result()`；模型下一轮能看到结构化拒绝结果。
7. `ASK`：从队列取出该 call 放入 `_pending_permission`，状态改为 `WAITING_PERMISSION`，yield `PermissionRequiredEvent` 并结束当前 generator。此时不执行工具、不继续请求 LLM。
8. 队列清空后，才发起下一轮 LLM 请求；若 LLM `is_stop`，状态回到 `IDLE` 并 yield 原始结束事件。

`_append_tool_result()` 必须统一使用：

```python
self.context.append_msg({
    "type": "function_call_output",
    "call_id": call_id,
    "output": self.tools.encode_result(result),
})
```

原因是 `Tools.encode_result()` 已经保证普通结果为 JSON 字符串、附件结果为 Responses content 数组。Runtime 不应自行拼接 `output`。

### 7.3 新增 `Runtime.resolve_permission()`

新增公共恢复接口：

```python
def resolve_permission(
    self,
    response: PermissionResponse,
) -> Generator[LLMEvent | PermissionRequiredEvent, None, None]:
    ...
```

逻辑：

1. 验证状态为 `WAITING_PERMISSION` 且 `response.call_id` 与 `_pending_permission.call.call_id` 相同；否则抛出内部 `InvalidPermissionResponseError`，由 CLI 显示错误，但不修改状态。
2. `ALLOW` 时调用 `permission.grant(request, response.scope, tools.default_grant_resource(request))`。
3. `DENY` 时调用 `permission.deny(...)`；随后为当前 call 生成 `PERMISSION_DENIED` 的 `ToolResult`。若未来 UI 要提供“只拒绝、不记规则”，再新增明确的 `cancel_permission()`，不要偷用不符合语义的 scope。
4. 清除 `_pending_permission`，状态恢复 `RUNNING`。
5. 对允许结果执行 `tools.execute()`，或对拒绝结果直接追加 output。
6. 调用 `_drain_tool_queue()`：它可能产生下一个 `PermissionRequiredEvent`；若没有，再进入 `_run_llm_loop()`。
7. 每个 call 只能恢复一次。处理后重复确认同一 `call_id` 必须失败，不能重复执行写入或 bash。

### 7.4 修改 `code/agent/runtime/agent.py`

新增：

```python
def resolve_permission(self, response: PermissionResponse):
    return self.runtime.resolve_permission(response)
```

Agent 是 CLI 的稳定入口；CLI 不需要知道 `PendingToolCall`、工具队列或 Context 的结构。

阶段四验收：模拟 LLM 产生 write 调用时，`BUILD` 模式先 yield `PermissionRequiredEvent`；允许后只写一次并继续；拒绝后模型收到结构化失败；同轮多个 function call 的顺序不丢失。

## 8. 阶段五：CLI 权限交互

### 8.1 修改 `code/cli/main.py`

新增函数：

```python
def render_permission_request(event: PermissionRequiredEvent) -> None: ...
def read_permission_response(event: PermissionRequiredEvent) -> PermissionResponse: ...
def run_agent_events(events, agent) -> None: ...
```

改动方式：

- `render_event()` 增加 `permission_required` 分支，清晰显示工具名、动作、真实规范化资源、当前模式和可选 scope。
- `read_permission_response()` 仅产生 `PermissionResponse`，不直接写规则。
- `run_agent_events()` 在遇到 `PermissionRequiredEvent` 时读取用户输入，调用 `agent.resolve_permission(response)`，并递归或循环消费恢复后的事件流。
- `/clear` 在 `WAITING_PERMISSION` 时必须拒绝或先要求处理 pending call，避免上下文被清空后仍恢复旧函数调用。
- `/exit` 不需要写规则；内存的 `ONCE/SESSION/AGENT` 规则随进程结束消失，这是首版有意的边界。

首版交互建议为六项：

```text
1. 允许本次
2. 当前会话允许
3. 当前 Agent 允许
4. 拒绝本次
5. 当前会话拒绝
6. 当前 Agent 拒绝
```

CLI 显示的是 `PermissionRequest.resource`，而非原始相对路径；这样用户能看见 Agent 实际要访问的位置。

### 8.2 不修改 `context/context.py` 的理由

`Context` 的职责仍然是保存 Responses input item。权限确认事件不写入模型上下文，只有最终 `function_call_output` 写入，因此本期不为 Context 增加权限状态、规则或 UI 字段。这样可以避免对上下文序列化协议造成无关耦合。

阶段五验收：CLI 发生 `ASK` 时不会卡死或继续执行；用户确认后控制权回到同一 Agent loop；输入非法选择不会误执行工具。

## 10. 推荐提交顺序

每个提交只包含一个可验证的语义变化，便于回滚和排查。

1. `permission: add domain types and execution identities`
   修改 `types.py`、`__init__.py`、`ExecutionContext.py`、`agent.py`、四个工具声明和已有测试构造器。

2. `permission: add pure policies and rule matching`
   新增 `policies.py`，实现 `PermissionManager.check/grant/deny` 与 Manager 单测；不改 Runtime 流程。

3. `tools: prepare tool calls before execution`
   新增 `PreparedToolCall`，替换 `eval()` 为 `prepare_call/execute/encode_result`，补工具准备单测。

4. `runtime: pause tool execution for permission confirmation`
   增加 Runtime 状态机、pending call、队列和 `resolve_permission()`，补 Runtime 单测；先不修改 CLI。

5. `cli: add permission confirmation interaction`
   接入权限事件显示和确认输入，完成手工验证。

提交之间不要混入 MCP、skills、子 Agent 或磁盘持久化。它们可在本计划完成、契约稳定后以独立变更接入。

## 11. 关键风险与验收闸门

| 风险 | 防护措施 | 完成闸门 |
| --- | --- | --- |
| `ASK` 后工具仍然执行 | 所有实际调用集中在 `Tools.execute()`，仅在 Runtime 收到 `ALLOW` 后调用 | Runtime 测试断言 ask 分支调用次数为 0。 |
| 用户确认恢复错调用 | `PermissionResponse` 仅含 `call_id`，Runtime 对比 pending call | 错误 call_id 与重复确认测试。 |
| 宽路径规则误匹配相邻目录 | 用 `commonpath` 或路径组件比较，而非 `startswith` | `/src` 不匹配 `/src-other` 测试。 |
| yolo 绕过安全边界 | 硬安全、受保护策略先于规则和模式 | yolo + hard/protected 测试。 |
| 工具输出格式被权限改坏 | Runtime 只能调用 `Tools.encode_result()` | 现有 ToolResult 契约测试与附件回归测试。 |
| 多 function call 被丢弃 | Runtime 使用 FIFO 队列 | 同轮双调用恢复测试。 |
| Agent 规则意外退化为 session | 引入稳定 `agent_key`，不复用随机实例 ID | 跨 session、同 agent_key 匹配测试。 |

## 12. 本计划完成后再做什么

完成本计划后，下一项应是 harness 安全层，而不是立即持久化规则。原因是当前的路径仍可在工具实际执行时被软链接、工作目录外资源或 bash 的副作用绕过；规则持久化只会把尚未可靠定义的边界保存得更久。

harness 阶段稳定后，再按相同 `PermissionRequest` 契约接入 MCP 和子 Agent：

- MCP tool 注册时转换为 `Tool` + `PermissionRequirement`，不能绕过 Runtime 的预检。
- 每个子 Agent 使用独立 `agent_key`、`session_id`、`PermissionManager` 和 mode。
- 父 Agent 的 `ONCE/SESSION` 规则不继承给子 Agent；是否继承 `AGENT` 规则应在子 Agent 设计阶段单独决定。
