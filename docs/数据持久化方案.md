# 数据持久化方案

## 1. 目标与边界

本方案为 Harness 建立一套本地持久化模型，用来保存两类不同生命周期的数据：

- **配置数据**：LLM 配置、逻辑 Agent 配置、Agent 启用的工具、Agent 范围权限规则。
- **运行数据**：会话、会话参与的 Agent、会话上下文、工具调用及其结果。

它解决的不是“把某个 Python 对象序列化到文件”这一件事，而是让程序重启后仍能回答以下问题：

```text
这个 workspace 中有哪些 Agent？
某个 Agent 使用哪套 LLM、启用了哪些工具、默认权限模式是什么？
这次会话有哪些 Agent 参与？
某条消息、function call 或 tool output 由谁产生？
恢复会话时，应该给某个 Agent 还原哪些上下文？
```

首期使用 SQLite，数据库仍位于：

```text
<workspace>/.harness/state.db
```

这表示 workspace 是第一层数据边界：不同项目的 Agent、会话和授权默认互不影响。`.harness/` 不进入版本控制。

本方案不保存以下内容：

- API Key、Token 等明文凭据。
- Python 工具函数、JSON Schema 的源码副本。
- workspace 中的普通项目文件。
- `ONCE` 和 `SESSION` 范围的权限规则。
- 操作系统级沙箱或文件系统安全边界。

## 2. 统一术语

“Agent”在运行时和持久化时含义不同，必须拆开，避免后续把短生命周期对象误当成配置对象保存。

| 术语 | 含义 | 生命周期 |
| --- | --- | --- |
| `AgentProfile`（Agent 配置） | 一个可复用的逻辑 Agent，例如 `coder`、`reviewer`。它指定 LLM、工具集、指令和默认权限模式。 | 跨进程、跨会话 |
| `Agent`（运行时对象） | 由 `AgentProfile` 加载出的实际 Python 对象，包含 LLM 客户端、Runtime、Tools、Context 等。 | 当前进程 |
| `Session`（会话） | 围绕一个用户任务持续的对话与执行记录。它属于 workspace，不属于单个 Agent。 | 可恢复 |
| `SessionParticipant`（会话参与者） | 表示某个 `AgentProfile` 参与某个 `Session` 的关系。 | 会话期间及历史 |
| `ContextItem`（上下文项） | 会话时间线中的一项：用户消息、Agent 消息、function call、function call output 等。 | 可恢复 |
| `LLMProfile`（LLM 配置） | 可复用的模型连接及调用参数，不携带明文凭据。 | 跨进程、可被多个 Agent 使用 |

因此，当前 `Agent.agent_key` 应继续表示稳定的逻辑身份；新建会话时生成的 `session_id` 则表示一次具体会话，二者不能互换。

## 3. 总体关系

```text
LLMProfile 1 ───── * AgentProfile
                         │
                         ├──── * AgentToolConfig * ──── 1 ToolDefinition（代码注册表）
                         │
                         └──── * PermissionRule（仅 AGENT 范围）

Session 1 ───── * SessionParticipant * ──── 1 AgentProfile
   │
   ├──── * ContextItem ──── * ContextItemTarget
   └──── * AgentDelegation（可选的委托/协作任务链）
```

其中 `ToolDefinition` 不是数据库中保存的 Python 函数，而是代码中的受信任工具注册表。数据库只决定某个 Agent 是否启用某个已注册工具，以及该工具的可配置参数。

## 4. 配置层

### 4.1 `llm_profiles`

LLM 配置必须独立于 Agent 保存。这样同一个 workspace 可以有多组模型配置，例如代码 Agent 使用代码模型，摘要 Agent 使用低成本模型；多个 Agent 也可以复用同一条配置。

```sql
CREATE TABLE llm_profiles (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL UNIQUE,
    provider TEXT NOT NULL,
    base_url TEXT,
    model TEXT NOT NULL,
    api_key TEXT NOT NULL,
    options_json TEXT NOT NULL DEFAULT '{}',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

字段约束：

- `api_key` 保存服务商 API Key；它只允许写入本地 workspace 数据库。列表、普通详情、日志、异常和导出配置都不得返回明文；编辑指定 LLM 配置时，可由本地 Web UI 的专用接口读取并默认遮蔽显示。
- `options_json` 保存温度、最大输出长度等可扩展调用参数。读取时必须按白名单校验，而不是把任意 JSON 直接传给供应商 SDK。
- Agent 的角色指令不放在这里。角色指令属于 Agent，而不是模型连接；否则两个使用同一模型的 Agent 会被迫共用人格与职责。

### 4.2 `agent_profiles`

```sql
CREATE TABLE agent_profiles (
    id TEXT PRIMARY KEY,
    agent_key TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    personality TEXT NOT NULL DEFAULT '',
    expertise_json TEXT NOT NULL DEFAULT '[]',
    llm_profile_id TEXT NOT NULL REFERENCES llm_profiles(id),
    instructions TEXT NOT NULL DEFAULT '',
    permission_mode TEXT NOT NULL,
    is_enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

`agent_key` 是程序使用的稳定标识，例如 `coder`；`name` 是供 UI 显示的可修改名称。权限系统中的 `PermissionRequest.agent_key` 继续使用前者，避免用户修改显示名后丢失授权归属。

`description`、`personality` 和 `expertise_json` 是 Agent 的可发现信息：用户选择 Agent 时可以看到它们，路由器也可以根据擅长领域筛选候选 Agent。它们与 `instructions` 不完全相同：前者面向用户和 Agent 选择逻辑，后者是发送给 LLM 的行为约束。`expertise_json` 首期只保存字符串标签数组，例如 `["python", "代码审查"]`，不要一开始建立复杂的技能图谱。

`permission_mode` 保存该 Agent 的默认模式，例如 `PLAN`、`BUILD`、`YOLO`。它不是一次运行临时传入的开关，而是 Agent 配置的一部分；UI 可以在创建会话或运行前覆盖它，但覆盖值不应自动写回配置。

### 4.3 工具代码注册与 `agent_tool_configs`

工具有两部分，不能混在一起：

```text
代码注册表（ToolDefinition）
  - tool name
  - Python callable
  - JSON Schema
  - PermissionRequirement

数据库关联（AgentToolConfig）
  - 哪个 Agent 启用哪个已注册工具
  - 工具对该 Agent 的可选配置
```

```sql
CREATE TABLE agent_tool_configs (
    agent_profile_id TEXT NOT NULL REFERENCES agent_profiles(id),
    tool_name TEXT NOT NULL,
    is_enabled INTEGER NOT NULL DEFAULT 1,
    config_json TEXT NOT NULL DEFAULT '{}',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (agent_profile_id, tool_name)
);
```

首期 `tool_name` 必须在代码注册表中存在，例如 `read`、`write`、`edit`、`bash`。加载 Agent 时，仓储先读出启用工具名，`Tools.register_by_names()` 再从代码注册表导入真正的 `Tool` 对象。数据库中未知或已移除的工具名属于配置错误，不能静默忽略。

`config_json` 只存工具明确声明为可配置的字段；它不能覆盖 `PermissionRequirement`、函数路径或 Schema。这样配置层不能把一个安全声明较弱的工具替换成任意 Python 可调用对象。

### 4.4 权限规则

权限规则仍然沿用当前设计：

- `ONCE`：只关联 `call_id`，仅存 Runtime 内存。
- `SESSION`：只关联 `session_id`，仅存 Runtime 内存；恢复会话后不自动恢复这类授权。
- `AGENT`：关联稳定 `agent_key`，持久化为 `permission_agent_rules`。

因此权限规则是 `AgentProfile` 的安全配置，而不是 `Session` 的属性。已有的《权限规则持久化方案》保留为本方案的权限子方案；实现时应把其中的表迁移纳入同一个 `StateDatabase` 版本体系，而不是创建第二个数据库。

## 5. 会话与多 Agent 协作

### 5.1 `sessions`

会话只表示一个任务的容器和生命周期，不保存单个 `agent_id`。`conversation_mode` 表达用户选择的交互形态，但不限制参与者数量；一对一会话中发生委托后，仍然可以继续使用同一个 Session。

首期定义三个模式：

- `DIRECT`：用户首先选择一个主 Agent 进行对话。主 Agent 可以按需委托其他 Agent。
- `GROUP`：用户在开始时选择多个 Agent，用户消息默认面向群组中的所有活跃 Agent。
- `OPEN`：允许参与的 Agent 在没有用户逐条发言的情况下互相对话；Runtime 需要设置轮次、预算和终止条件。

模式是默认的交互策略，不是数据库权限。即使是 `DIRECT`，也不能据此拒绝合法的 Agent 委托；是否允许委托应由后续的编排策略和权限策略共同决定。

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    title TEXT,
    conversation_mode TEXT NOT NULL,
    status TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    closed_at TEXT
);
```

不能在 `sessions` 上增加单个 `agent_profile_id`，原因是：

```text
用户在一个任务中先与 coder 对话
  -> coder 交给 reviewer 检查
  -> reviewer 的结论回到 coder
  -> 用户继续追问
```

它们是同一任务、同一会话，但有多个 Agent 参与。

### 5.2 `session_participants`

```sql
CREATE TABLE session_participants (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL REFERENCES sessions(id),
    agent_profile_id TEXT NOT NULL REFERENCES agent_profiles(id),
    role TEXT NOT NULL,
    join_reason TEXT NOT NULL,
    joined_at TEXT NOT NULL,
    left_at TEXT,
    UNIQUE (session_id, agent_profile_id)
);
```

首期 `role` 只需要 `PRIMARY` 与 `PARTICIPANT`：前者是用户最初选择的主 Agent 或群聊主 Agent，后者表示协作 Agent。`join_reason` 可取 `USER_SELECTED`、`DELEGATED`、`AUTO_JOINED`，用于 UI 解释某个 Agent 为什么出现在会话中。

参与关系和委托关系不是一回事：参与关系表示“谁在这个会话中”，委托关系表示“谁因为哪项工作请求谁处理”。后者通过上下文事件或 `AgentDelegation` 保存，不能把 `parent_participant_id` 直接塞进参与者表，否则一个 Agent 多次被委托时无法表达。

一个 Agent 可参与多个 Session，一个 Session 也可包含多个 Agent。重新打开会话时，应先根据该表恢复可参与的 Agent，再决定由哪个 Agent 继续处理。

## 6. 上下文持久化

### 6.1 `context_items` 是会话时间线

会话上下文不是某个 Agent 的私有字段，而是 Session 的有序事件流。首期使用一张追加式时间线表保存上下文项：

```sql
CREATE TABLE context_items (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL REFERENCES sessions(id),
    sequence_no INTEGER NOT NULL,
    kind TEXT NOT NULL,
    author_participant_id TEXT REFERENCES session_participants(id),
    visibility TEXT NOT NULL,
    call_id TEXT,
    caused_by_item_id TEXT REFERENCES context_items(id),
    payload_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE (session_id, sequence_no)
);

CREATE INDEX idx_context_items_session_sequence
    ON context_items(session_id, sequence_no);

CREATE INDEX idx_context_items_call_id ON context_items(call_id);
```

由于群聊和 Agent 间对话可能有多个接收者，目标不再作为 `context_items` 的单值字段保存，而单独建关联表：

```sql
CREATE TABLE context_item_targets (
    context_item_id TEXT NOT NULL REFERENCES context_items(id),
    participant_id TEXT NOT NULL REFERENCES session_participants(id),
    PRIMARY KEY (context_item_id, participant_id)
);
```

`visibility` 首期取值为：

- `PUBLIC`：会话中的所有活跃 Agent 都可见，适合群聊和公开的 Agent 间讨论；目标表为空。
- `TARGETED`：只发送给目标表中的 Agent，适合 Agent 委托和定向回复。
- `PRIVATE`：只属于作者的内部工作记录，目标表为空，不进入其他 Agent 的上下文。

用户消息的 `author_participant_id` 为空；用户消息可以是 `PUBLIC`，也可以通过目标表定向发送给一个或多个 Agent。Agent 消息的作者必须是参与者。这样同一套模型同时覆盖“用户与一个 Agent 对话”“用户群聊”“Agent 自由对话”，不会把用户强行建模成一个 Agent。

参与者的 `joined_at` 只决定默认可见范围，不代表新 Agent 可以读取会话的全部历史。委托方必须在 `AGENT_DELEGATION` 的 payload 中携带任务说明和被选中的上下文引用，或由 `ContextService` 根据明确的共享策略提供必要摘要；不能因为某些历史项是 `PUBLIC` 就自动把完整历史发送给刚加入的 Agent。这样既支持委托所需的上下文，又避免无意泄露早期对话或其他 Agent 的私有工作记录。

推荐的 `kind` 为：

- `USER_MESSAGE`
- `AGENT_MESSAGE`
- `FUNCTION_CALL`
- `FUNCTION_CALL_OUTPUT`
- `AGENT_DELEGATION`
- `SYSTEM_EVENT`

function call 和 function call output 都应记录其执行 Agent。`caused_by_item_id` 用于记录因果关系，例如某个 Agent 的 `AGENT_DELEGATION` 事件触发了另一个 Agent 的消息、工具调用和最终结果。它是事件链，不等价于消息接收目标。

`call_id` 用来把 `FUNCTION_CALL` 与 `FUNCTION_CALL_OUTPUT` 精确配对。工具输出不能只作为一段普通文本保存，否则恢复时无法可靠地还原模型所需的调用关系。

### 6.2 `payload_json` 的边界

`payload_json` 保存 Harness 自己定义的、已校验的 `ContextItem` 内容，而不是直接把某个供应商的完整请求体塞进数据库。模型供应商适配器负责将内部上下文转换为 OpenAI Responses 或未来其他厂商的协议。

例如，工具结果可存为：

```json
{
  "status": "ok",
  "data": {"path": "test/a.txt", "text": "..."},
  "attachments": [{"artifact_id": "artifact_xxx", "media_type": "image/png"}]
}
```

这样 `ToolResult` 的统一契约仍在工具层生效，持久化层不需要知道 `input_text`、`input_image` 等 Responses 字段。恢复时由 Context/LLM 适配层重新编码。

### 6.3 每个 Agent 如何获得上下文

Session 的完整时间线不等于每一次模型请求都要原样发送给所有 Agent。恢复或调用某个 Agent 时，应由 `ContextService` 基于 `visibility`、目标关联和参与时间构造其可见上下文：

```text
Session 全部时间线
  -> 保留该 Agent 加入后产生的 PUBLIC 项
  -> 保留目标包含该 Agent 的 TARGETED 项
  -> 保留该 Agent 自己的 PRIVATE 项
  -> 通过 caused_by_item_id 关联其委托任务的必要上下文
  -> 按上下文窗口执行截断/摘要
  -> 加入该 AgentProfile.instructions
  -> 交给 LLM 适配器
```

在 `DIRECT` 模式中，用户消息默认只投递给 PRIMARY Agent；委托产生的定向项投递给被委托 Agent，委托结果再定向返回请求 Agent。`GROUP` 模式中，用户消息默认是 PUBLIC；`OPEN` 模式中，Agent 消息默认可以是 PUBLIC，但编排器必须限制最大轮数、消息预算和空转检测。

这里的“默认”只负责生成消息目标，不是绕过权限的机制。用户或编排器可以明确指定目标，但 Runtime 仍必须检查参与状态、可见性策略和 Agent 间通信权限。

若未来需要把某个 Agent 的长会话压缩为摘要，应新增 `session_context_snapshots` 或 `agent_session_state` 保存摘要与游标；不要覆写原始 `context_items`，否则无法审计或重新选择摘要策略。

### 6.4 二进制附件与大结果

SQLite 保存元数据和结构化内容，不应保存大文件或二进制内容。新增附件支持时使用：

```text
<workspace>/.harness/artifacts/<artifact-id>
```

并通过 `artifacts` 表记录 `id`、MIME 类型、文件名、相对路径、大小、校验值和创建时间。`ContextItem.payload_json` 只引用 `artifact_id`。这与现有 `Attachment` 的 `bytes/url` 设计兼容：

- 本地 `bytes`：落入 artifact 文件，再持久化引用。
- URL：可保存 URL 与 MIME 元数据；是否下载由工具语义决定，不能由存储层擅自下载。
- Base64：只是传输编码，不能作为长期领域类型或存储模型。

对于很大的 `read` / `bash` 输出，应由 `ContextService` 制定截断与摘要策略，并在原始结果是否保留上设置明确上限；不能无上限地让数据库和模型上下文一起膨胀。

### 6.5 委托与 Agent 间自由对话

建议用一张轻量的委托任务表记录可追踪的工作委托；自由聊天不必为每条消息创建任务。

```sql
CREATE TABLE agent_delegations (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL REFERENCES sessions(id),
    requester_participant_id TEXT NOT NULL REFERENCES session_participants(id),
    worker_participant_id TEXT NOT NULL REFERENCES session_participants(id),
    request_item_id TEXT NOT NULL REFERENCES context_items(id),
    parent_delegation_id TEXT REFERENCES agent_delegations(id),
    status TEXT NOT NULL,
    result_item_id TEXT REFERENCES context_items(id),
    created_at TEXT NOT NULL,
    completed_at TEXT
);
```

这张表支持“委托树”和 UI 展示，例如用户可以看到 coder 委托 reviewer，reviewer 又委托 tester。它不取代上下文时间线：具体请求、工具调用和结果仍然写入 `context_items`。

对于 Agent 自由对话，只写入 `AGENT_MESSAGE`，用 `PUBLIC` 或 `TARGETED` 表示可见范围；只有当一方明确要求另一方完成工作时，才创建 `agent_delegations`。这避免把所有 Agent 发言都错误地解释成任务。

`agent_delegations.status` 首期可取 `PENDING`、`RUNNING`、`COMPLETED`、`FAILED`、`CANCELLED`。`OPEN` 模式下还必须有 Runtime 级终止条件，不能因为数据库允许 Agent 互发消息就让会话无限运行。

## 7. 存储模块边界

建议目录结构如下：

```text
code/agent/
  storage/
    database.py              # SQLite 连接、事务、schema 版本与迁移
    migrations/              # 每个版本的增量 schema
    repositories/
      llm_profile.py
      agent_profile.py
      session.py
      context_item.py
      permission_rule.py
      artifact.py             # 需要附件持久化时再实现
    runtime/
    agent_factory.py          # 根据 AgentProfile 组装运行时 Agent
    context_service.py        # 从会话时间线恢复并投影可见上下文
    orchestration_service.py  # 处理 Agent 选择、委托和群聊调度
```

职责必须保持清楚：

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| `StateDatabase` | 连接、事务、迁移、版本校验 | 领域规则、构造 Runtime |
| Repository | 行与领域对象的转换、CRUD、读取校验 | 权限判断、LLM 调用 |
| `AgentFactory` | 读取配置并组装 `Agent`、`Tools`、`PermissionManager` | SQL 拼接、会话消息排序 |
| `ContextService` | 追加时间线、恢复和投影 Agent 可见上下文 | 直接执行工具 |
| `OrchestrationService` | 选择/加入 Agent、创建委托、推进群聊和自由对话轮次 | 修改权限规则、直接操作 LLM 协议 |
| `PermissionManager` | 根据请求与内存/持久规则作 `ALLOW/DENY/ASK` 决定 | 直接操作 SQLite |
| Runtime | 驱动 LLM、工具、暂停与恢复，并把已发生事件交给 ContextService | 自己管理表和迁移 |

特别地，`Agent` 不应变成“既创建数据库、又执行 SQL、又调 LLM、又管理会话”的大对象。它应由 `AgentFactory` 组装；Repository 通过明确接口注入，而不是让工具或 Runtime 到处访问数据库连接。

## 8. 读写流程

### 8.1 创建或加载 Agent

```text
AgentFactory.load(agent_key)
  -> AgentProfileRepository 读取 AgentProfile
  -> LLMProfileRepository 读取 LLMProfile（包含 api_key）
  -> ToolCatalog 校验并注册已启用工具
  -> PermissionRuleRepository 读取该 agent_key 的 AGENT 规则
  -> 组装短生命周期的 Agent / Runtime
```

数据库配置不合法、API Key 为空或工具名未注册时，加载应明确失败。不能为了“能启动”而悄悄换成默认模型、忽略工具或放松权限。

### 8.2 新建或恢复 Session

```text
创建 DIRECT：SessionRepository.create(mode=DIRECT)
  -> 用户选择 AgentProfile
  -> SessionParticipantRepository.add(primary Agent, join_reason=USER_SELECTED)
  -> ContextService.append(USER_MESSAGE, target=primary)

创建 GROUP：SessionRepository.create(mode=GROUP)
  -> 用户选择多个 AgentProfile
  -> 批量加入 SessionParticipant
  -> ContextService.append(USER_MESSAGE, visibility=PUBLIC)

创建 OPEN：SessionRepository.create(mode=OPEN)
  -> 加入允许自主交流的 AgentProfile
  -> OrchestrationService 按预算推进 Agent 消息

恢复：SessionRepository.get(session_id)
  -> 读取 SessionParticipant
  -> ContextService.load_visible_context(agent_key)
  -> AgentFactory.load(agent_key)
  -> Runtime 继续
```

将协作 Agent 加入已存在会话时，只增加一条 `SessionParticipant`，并追加一条系统事件说明加入原因；不复制整个会话，也不把会话“转移”给另一个 Agent。

### 8.3 一次 Runtime 运行

```text
用户消息
  -> 先追加 USER_MESSAGE
  -> LLM 输出 Agent 消息 / function call，追加对应 ContextItem
  -> Runtime 执行工具
  -> 追加 FUNCTION_CALL_OUTPUT
  -> 再发起下一轮 LLM 请求
```

委托分支为：

```text
PRIMARY Agent 产生 AGENT_DELEGATION
  -> 加入或激活目标 Agent Participant
  -> 目标 Agent 获得目标项及必要的公开上下文
  -> 目标 Agent 执行消息/工具调用
  -> 结果定向返回请求 Agent，或按策略公开到群聊
```

上下文项按发生顺序使用一个事务写入。对“function call 已保存但工具输出尚未保存”的中断情形，恢复时需要显式标记为未完成，而不能伪造成功输出；具体恢复策略在实现阶段单独确定。

## 9. 数据安全与一致性

- 使用 SQLite 事务、参数绑定、`foreign_keys = ON` 和 schema version 迁移。
- 对 `agent_key`、枚举值、JSON 结构和 workspace 相对 artifact 路径进行严格校验；损坏的权限规则必须失败关闭。
- API Key 仅从本地 workspace 数据库读取；日志、异常、列表、普通详情和导出配置均不出现明文。仅编辑指定 LLM 配置的本地 Web UI 专用接口可以返回该配置的 API Key。
- `state.db` 与 `artifacts/` 默认放在 `.harness/` 并仅允许当前用户读写；实际权限设置需考虑操作系统差异。
- LLM 输入、工具输出和附件可能含敏感数据。UI 必须让用户看见它们会被保存，并提供“删除会话 / 清除本地状态”的显式入口；程序不能自行清理历史。
- 数据删除必须按实体关系执行：删除 Session 时删除其 participant、context item 与仅被该 Session 引用的 artifact；删除 AgentProfile 前必须检查其是否仍被 SessionParticipant 或权限规则引用。

## 10. 首期表与实现范围

第一轮不需要一次实现所有表。推荐按可用闭环拆分：

1. `schema_metadata`、`llm_profiles`、`agent_profiles`、`agent_tool_configs`：能够创建并从配置加载一个 Agent。
2. 迁入 `permission_agent_rules`：把已完成的权限模型接到统一状态库，持久化 `AGENT` 规则。
3. `sessions`、`session_participants`、`context_items`、`context_item_targets`：能够支持 DIRECT、GROUP 和 Agent 间消息，并按目标恢复上下文。
4. `agent_delegations` 与 `OrchestrationService`：支持委托链、结果回传和失败恢复。
5. Context 恢复与投影：让重新打开的会话真正继续，而不是只在数据库中看见历史。
6. `artifacts`：在图片、音频、文件等附件工具实际接入后实现，避免提前造出没有消费者的二进制存储。

SQLite schema 从第一版开始采用迁移版本，不通过“表是否存在”猜测状态。此前《权限规则持久化方案》中的 `schema_metadata` 可作为同一套迁移机制的基础。

## 11. 尚待在开发计划中确定的细节

以下问题不应靠实现时临时决定：

- `LLMProfile.options_json` 第一批允许哪些参数，以及每个 provider 的校验规则。
- Session 中断在 `FUNCTION_CALL` 和 `FUNCTION_CALL_OUTPUT` 之间时，是重试、标记失败，还是要求用户确认。
- 多 Agent 的公开项和定向项在 UI 中如何展示，以及何时允许某 Agent 看见另一个 Agent 的私有上下文。
- 何时需要跨 workspace 的全局 LLM 配置；首期不引入第二个全局数据库。
- 会话与 artifact 的删除、导出、备份策略。

这些是后续开发计划应明确列出的实现决策；在此之前，不应直接把当前内存对象用 `pickle` 或无结构 JSON 保存下来。
