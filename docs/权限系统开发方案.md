# 权限系统开发方案

## 1. 目标与边界

本期为 Agent 的工具调用增加可解释、可确认、可恢复的权限控制。它解决的是“当前 Agent 能否对某个资源执行某个动作”，而不是文件系统沙箱或操作系统级隔离。

本期目标：

- 所有工具调用在真正执行前完成权限决策。
- 决策统一为 `allow`、`deny`、`ask` 三种结果。
- `ask` 可以暂停当前调用，等待用户选择后按原参数恢复执行。
- 用户可按“本次 / 当前会话 / 当前 Agent”保存允许或拒绝规则。
- 权限模式提供默认策略；绝对黑名单和受保护资源优先于模式。
- 继续保持 `ToolResult` 是工具执行结果的唯一内部契约。



## 2. 核心原则

1. 工具声明“需要什么权限”，调用时再解析成“此次调用访问什么资源”。
2. `PermissionManager` 只做策略和规则判断，不调用工具，也不负责 UI 或 Runtime 的暂停。
3. `Runtime` 只编排状态机：允许则执行，拒绝则产出工具失败结果，询问则挂起并等待恢复。
4. 权限拒绝是预期业务结果，不应以未捕获异常的形式传播。
5. 所有规则按动作和资源匹配；文件操作的交互默认授予目录子树，而非每个文件单独授予。
6. 硬安全边界优先级最高，`yolo` 也不能绕过绝对黑名单。

## 3. 领域模型

现有 `Permission` 名称容易和“用户已授予的规则”混淆，建议改为 `PermissionRequirement`。它是工具静态元数据，不是一次实际授权。

```python
class PermissionAction(StrEnum):
    FILE_READ = "filesystem.read"
    FILE_WRITE = "filesystem.write"
    BASH_EXECUTE = "bash.execute"


@dataclass(frozen=True)
class PermissionRequirement:
    action: PermissionAction
    resource_from: str | None


class PermissionDecision(StrEnum):
    ALLOW = "allow"
    DENY = "deny"
    ASK = "ask"


class PermissionScope(StrEnum):
    ONCE = "once"
    SESSION = "session"
    AGENT = "agent"


@dataclass(frozen=True)
class PermissionRequest:
    action: PermissionAction
    resource: str | None
    call_id: str
    session_id: str
    agent_key: str
    tool_name: str


@dataclass(frozen=True)
class PermissionRule:
    action: PermissionAction
    resource: str | None
    decision: PermissionDecision  # 只允许 ALLOW / DENY
    scope: PermissionScope
    call_id: str | None = None
    session_id: str | None = None
    agent_key: str | None = None
```

约束：

- `PermissionRequirement.resource_from` 是参数名，例如 `target_path`；无确定资源时为 `None`，例如首版 `bash.execute`。
- `PermissionRequest.resource` 总是本次调用的实际资源。文件路径应在构造阶段规范化为绝对路径；这不等于本期实施 workspace 越界阻断。
- `PermissionRule.resource` 表示规则覆盖的根目录或精确资源。首版普通文件授权由确认层把目标文件提升为父目录。
- `ONCE` 规则必须绑定 `call_id`；`SESSION` 必须绑定 `session_id`；`AGENT` 必须绑定稳定的 `agent_key`。
- 现有随机 `aid` 只能标识实例，不能表达“同一 Agent 的后续会话”。因此 `Agent` 需要引入可配置、稳定的 `agent_key`；`sid` 则每次会话创建。

`ExecutionContext` 负责携带执行身份和环境：`workspace`、`agent_key`、`session_id`、`max_tool_call_length`。它不保存规则，也不包含策略逻辑。

## 4. 工具声明与请求构造

每个 `Tool` 只有一份权限需求声明：

```python
Tool(
    schema=READ_SCHEMA,
    function=read,
    permission=PermissionRequirement(
        action=PermissionAction.FILE_READ,
        resource_from="target_path",
    ),
)
```

构造 `PermissionRequest` 的位置放在 `Tools`，因为它同时拥有工具声明、已验证参数和 `ExecutionContext`。建议添加：

```python
def build_permission_request(
    self,
    tool: Tool,
    arguments: dict[str, Any],
    call_id: str,
) -> PermissionRequest:
    ...
```

构造规则：

- 先由 `Tools.eval()` 解析并验证 `arguments` 为对象。
- 若 `resource_from` 存在，读取对应参数；缺少参数属于工具参数错误，不进入权限判断。
- 文件路径使用现有 `handle_path(ctx, target_path)` 转成绝对路径，并以 `normpath` 规范化。
- `bash` 首版生成 `resource=None`。它首先按 `bash.execute` 这一高风险动作判断，绝对黑名单可对原始命令做有限、明确的识别；不要试图从任意 shell 文本推导所有会访问的文件。

`Tools.eval()` 仍只负责调用工具和序列化 `ToolResult`，不应在其中直接做最终权限决策。原因是 `ask` 需要 Runtime 挂起循环并保存模型的 `call_id`。

## 5. PermissionManager 接口

```python
class PermissionManager:
    def check(self, request: PermissionRequest) -> PermissionDecision:
        """仅作同步、无副作用的策略判断。"""

    def grant(
        self,
        request: PermissionRequest,
        scope: PermissionScope,
        resource: str | None,
    ) -> PermissionRule:
        """写入 ALLOW 规则并返回规则。"""

    def deny(
        self,
        request: PermissionRequest,
        scope: PermissionScope,
        resource: str | None,
    ) -> PermissionRule:
        """写入 DENY 规则并返回规则。"""
```

首版将规则保存在 `PermissionManager` 的内存列表。`grant` / `deny` 不接收任意 action、agent 或 session 字段，而是从原始 `PermissionRequest` 派生，避免调用方误把规则写给另一 Agent 或会话。

规则匹配应固定且可测试：

- `action` 必须相同。
- `resource is None` 仅匹配同样为 `None` 的请求。
- 文件资源按路径边界进行子树匹配，`/repo/a` 不可匹配 `/repo/abc`。
- scope 的身份字段必须与请求一致。
- 同范围同资源的最新规则覆盖旧规则；不应让列表顺序成为隐式语义。

## 6. 决策顺序

`check()` 只返回决策。推荐固定以下优先级，任何后续功能都不能跳过前两层：

```text
绝对黑名单 / 硬安全边界          -> DENY
受保护路径或危险命令             -> ASK
已命中的明确 DENY 规则           -> DENY
已命中的 ONCE 规则               -> ALLOW / DENY
已命中的 SESSION 规则            -> ALLOW / DENY
已命中的 AGENT 规则              -> ALLOW / DENY
当前权限模式的默认策略            -> ALLOW / DENY / ASK
```

这里的“最具体”首先是规则作用域，再是资源路径深度：同一 scope 下，路径更深的规则优先。这样可以支持“允许 `src/`，拒绝 `src/.env`”而不增加另一套优先级模型。

### 绝对黑名单

绝对黑名单表达无条件禁止的行为，例如明显的破坏性系统命令、不可接受的系统关键资源修改。它不接受用户确认，也不能被 `yolo` 或普通规则覆盖。

首版应把黑名单实现为独立、可审计的策略函数或 `HardSafetyPolicy`，而不是散落在工具中。具体命令列表要小而保守，优先覆盖已确认的高危行为，避免把大量正常命令误判为绝对禁止。

### 受保护区域

受保护区域是“可在用户明确确认后执行”的资源，例如系统级目录或 Agent 自身配置目录。命中后直接 `ASK`，优先于已有允许规则和模式默认值，防止宽泛授权无意扩展到系统资源。

本期先将受保护路径配置为明确目录列表；完整的工作区边界、符号链接解析和跨平台系统目录枚举延后到 harness 层。

## 7. 权限模式

权限模式只回答“没有硬策略、受保护策略和显式规则命中时怎么办”。它不写入规则。

```python
class PermissionMode(StrEnum):
    PLAN = "plan"
    BUILD = "build"
    YOLO = "yolo"
```

首版默认值：

| 模式 | `filesystem.read` | `filesystem.write` | `bash.execute` | 项目外资源 |
| --- | --- | --- | --- | --- |
| `plan` | allow | deny | deny | 由受保护策略决定，否则 deny |
| `build` | allow | ask | ask | ask |
| `yolo` | allow | allow | allow | allow，但绝对黑名单仍 deny，受保护区域仍 ask |

`build` 的含义是“可以实施，但副作用必须由用户确认”。这比默认静默写入更符合当前项目的学习和调试阶段，也保留了之后针对可信工作区放宽写入的余地。

## 8. Runtime 暂停与恢复

当模型返回一个 `function_call` 时，Runtime 不应直接调用 `Tools.eval()`，而应走以下状态机：

```text
解析 function_call
  -> 取得 Tool 和参数
  -> Tools.build_permission_request(...)
  -> PermissionManager.check(request)
       -> ALLOW: Tools.eval(...) -> 写入 function_call_output -> 继续 LLM loop
       -> DENY : ToolResult.failure(PERMISSION_DENIED, ...) -> 写入 function_call_output -> 继续 LLM loop
       -> ASK  : 保存 PendingToolCall -> 返回/通知调用方，Runtime 进入 WAITING_PERMISSION
```

建议数据结构：

```python
@dataclass
class PendingToolCall:
    call_id: str
    tool_name: str
    arguments: dict[str, Any]
    request: PermissionRequest
```

确认接口由 Runtime 对外提供：

```python
def resolve_permission(
    self,
    call_id: str,
    decision: PermissionDecision,  # ALLOW 或 DENY
    scope: PermissionScope,
) -> RunResult:
    ...
```

恢复规则：

1. 仅接受当前 `PendingToolCall.call_id`，防止旧确认误恢复新调用。
2. `ALLOW` 时，Runtime 根据 request 计算默认授权资源。文件操作默认取目标父目录；`bash` 取 `None`。
3. 调用 `PermissionManager.grant()` 或 `deny()` 写入选择的 scope 规则。
4. 对这一个 pending call 执行原始工具，或生成拒绝的 `ToolResult.failure`。
5. 将该结果按现有 Responses 编码写入上下文，再从暂停位置继续 LLM loop。
6. 清除 pending 状态。再次调用 `resolve_permission` 必须失败，保证幂等边界清晰。

前端/CLI 不直接操作 `PermissionManager`；它只展示 `PermissionRequest`、收集用户选择，然后调用 Runtime 的恢复接口。这样以后换成交互式 CLI、Web UI 或 MCP host 都不会改变权限判断逻辑。

## 9. 工具结果与错误语义

权限拒绝必须走既有 `ToolResult`：

```python
ToolResult.failure(
    code="PERMISSION_DENIED",
    message="当前 Agent 无权写入该目录",
    retryable=False,
    details={"action": "filesystem.write", "resource": "/..."},
)
```

经 `Tools._encode_output()` 后，无附件时仍是 JSON 字符串；含附件时才是 Responses content 数组。权限系统不引入新的 `function_call_output` 格式，也不把 `ask` 当作工具输出发送给模型，因为此时工具调用尚未完成，应由宿主先向用户确认。

建议固定错误码：

- `PERMISSION_DENIED`：硬策略或显式拒绝规则阻止执行。
- `PERMISSION_REQUIRED`：仅用于 Runtime 向 CLI/UI 描述等待确认状态，不进入模型上下文。
- `INVALID_PERMISSION_RESPONSE`：确认了不存在或已处理的 pending call，或 scope 非法。

## 10. 实施顺序

### 阶段一：类型和上下文

- 将 `Permission` 调整为 `PermissionRequirement`，新增 request、rule、scope、mode、decision 类型。
- 为 `ExecutionContext` 增加 `agent_key` 和可靠的 `session_id`。
- `Agent` 支持显式传入稳定 `agent_key`，保留随机实例 ID 只作诊断用途。
- 迁移四个现有工具的静态权限声明。

验收：类型单测覆盖构造约束；无权限逻辑时工具调用行为不变。

### 阶段二：纯权限决策

- 实现 `PermissionManager.check/grant/deny` 和内存规则表。
- 实现路径规范化、目录子树匹配、scope 匹配和覆盖规则。
- 实现模式默认策略、绝对黑名单和受保护路径策略。

验收：该阶段不需要 LLM 或真实工具即可通过表驱动单测完整验证决策。

### 阶段三：Runtime 编排

- Runtime 在工具执行前构造 `PermissionRequest` 并调用 `check()`。
- 增加 `PendingToolCall`、`WAITING_PERMISSION` 状态和 `resolve_permission()`。
- 将 `DENY` 转换为 `ToolResult.failure`，并把恢复后的结果正确追加为 `function_call_output`。

验收：一次询问、一次确认、一次拒绝、重复确认和多次连续工具调用都能恢复到正确的 LLM loop。

### 阶段四：CLI 交互与可观测性

- CLI 展示动作、目标资源、工具名称和可选授权范围。
- 给出 `本次`、`当前会话`、`当前 Agent` 三个选择，以及拒绝。
- 记录决策来源：hard safety、protected、rule、mode，便于调试“为什么放行/阻止”。

验收：用户能看懂本次请求的真实目标，且不会因 UI 选择绕过 Runtime 校验。

### 阶段五：harness 安全层与扩展

- 将路径边界、符号链接解析、系统目录策略、进程/网络限制下沉到 harness。
- 为 MCP tools 映射相同的 `PermissionRequirement` / `PermissionRequest`；不让 MCP 自带 schema 绕过权限流程。
- 子 Agent 创建时分配独立 `agent_key`、权限模式和管理器；不得继承父 Agent 的 `ONCE`/`SESSION` 规则。
- 再考虑规则持久化和全局规则。持久化前先定义序列化版本与失效策略。

## 11. 测试清单

- `FILE_READ`、`FILE_WRITE`、`BASH_EXECUTE` 的三种模式默认结果。
- 绝对黑名单总是 `DENY`，即使存在 `AGENT` allow 或 `yolo`。
- 受保护路径总是 `ASK`，即使存在 allow 或 `yolo`。
- `ONCE` 规则只命中相同 `call_id`；`SESSION` 不跨 session；`AGENT` 跨 session 但不跨 `agent_key`。
- `/repo/src` 能匹配 `/repo/src/a.py`，不能匹配 `/repo/src-other/a.py`。
- 更深路径规则覆盖更浅路径规则。
- `ASK` 不执行工具；用户允许后只执行一次；拒绝后产生标准 `ToolResult.failure`。
- `function_call_output` 的 `call_id` 与原始调用一致，输出仍符合当前 Tools 编码契约。
- 无效的权限确认、过期确认、重复确认都不会重复执行工具。

## 12. 决策记录

- 授权范围是 `once/session/agent`，不在本期引入“永久规则”。
- `agent` 指逻辑 Agent，不是单个随机实例；需要稳定 `agent_key`。
- 普通文件操作按目录授权，底层仍保留精确路径匹配能力。
- `plan` 只读，`build` 对副作用询问，`yolo` 对普通资源默认允许但不能绕过绝对黑名单和受保护区域。
- `bash` 首版按动作整体授权；只对少量、明确的极危险命令做硬策略识别，不承诺完整 shell 语义分析。
