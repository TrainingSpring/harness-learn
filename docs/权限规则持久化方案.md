# 权限规则持久化方案

> 历史方案。当前产品只持久化 Session 级规则；详情见[权限收缩与项目会话迭代计划](plan/权限收缩与项目会话迭代计划.md)。

## 1. 目标

本方案只持久化权限系统中的 `AGENT` 范围规则，使同一项目中的同一逻辑 Agent 在新的会话、进程重启后仍能恢复已确认的授权。

当前 `PermissionManager._rules` 是内存列表：

```text
Agent 创建
  -> PermissionManager 创建
  -> _rules = []
  -> 用户选择“当前 Agent 允许”
  -> 规则只存在当前进程
  -> 退出后丢失
```

目标状态：

```text
Agent 创建
  -> 打开项目本地状态数据库
  -> 读取该 agent_key 的 AGENT 规则
  -> PermissionManager 载入规则
  -> 用户确认新的 AGENT 规则
  -> 原子写入数据库
  -> 下次创建同 agent_key 的 Agent 时恢复
```

## 2. 范围与非目标

本期做：

- 持久化 `PermissionScope.AGENT` 的文件读写规则。
- 按项目隔离规则：一个项目的授权不影响另一个项目。
- 按 `agent_key` 隔离规则：`code_editor` 不继承 `reviewer` 的授权。
- 原子写入、数据库版本管理、严格读取校验和失败关闭策略。
- 提供查询、覆盖和删除 Agent 规则的仓储接口，供以后 UI 的“权限管理”页使用。

本期不做：

- `ONCE`：绑定一次 `call_id`，调用结束即失效，绝不写入磁盘。
- `SESSION`：绑定本次 `session_id`，会话结束即失效，绝不写入磁盘。
- 对话消息、LLM 响应、工具完整输出、附件或文件内容的持久化。
- 权限审计日志、规则导入导出、云同步和全局规则。
- 操作系统级沙箱；持久化规则不会替代 harness 安全边界。

`PermissionMode` 也不在本期写入数据库。它属于 Agent 配置而不是用户具体授权；避免一次临时启动的 `yolo` 选择在下次启动时被静默恢复。

## 3. 核心决策：使用项目本地 SQLite

### 决策

使用 Python 标准库的 `sqlite3`，数据库位置为：

```text
<workspace>/.harness/state.db
```

`.harness/` 必须加入项目 `.gitignore`，不提交到版本库。

### 原因

规则数量很小，JSON 看起来也能满足需求，但它在以下场景会很快变得脆弱：

- 多个 Agent 或多个进程同时更新规则，容易丢失最后一次写入。
- 需要原子地“替换同一规则槽位”。
- 需要可靠处理损坏、版本迁移和唯一约束。
- 后续 UI 很可能需要持久化会话、Agent 配置或任务元数据；SQLite 可作为本地状态层基础，不需要再迁移 JSON。

SQLite 的优势：

- 无外部服务、无新增第三方依赖。
- 事务保证一次规则替换不会产生半写入文件。
- 唯一约束可在存储层防止同一规则槽位重复。
- 后续可增表，不要求一开始设计完整“大数据库”。

### 为什么不直接把所有状态放入一张 JSON 文件

JSON 适合静态配置，不适合由多个运行中的 Agent 频繁修改的规则状态。自行实现文件锁、临时文件替换、崩溃恢复、并发合并和版本迁移，最终复杂度会高于 SQLite。

## 4. 数据归属与授权语义

持久化授权的真实归属是：

```text
项目 workspace + agent_key + action + resource
```

例如：

```text
项目：/Volumes/project-a
Agent：code_editor
动作：filesystem.write
资源：src/
决定：allow
```

它不应影响：

```text
项目：/Volumes/project-b
Agent：code_editor
```

也不应影响：

```text
项目：/Volumes/project-a
Agent：reviewer
```

项目隔离由“每个 workspace 一个 `.harness/state.db`”天然实现；Agent 隔离由数据表中的 `agent_key` 实现。

### 文件资源保存为相对 workspace 的路径

内存中的 `PermissionRule.resource` 继续使用规范化绝对路径，因为运行时匹配绝对路径最清楚。

数据库中，项目内文件资源保存为相对 workspace 的路径：

```text
内存：/Volumes/project-a/src
数据库：src
```

原因：项目移动或复制到新目录后，规则仍能恢复到新 workspace，不会绑定旧机器上的绝对路径。

加载时必须执行：

```text
relative_resource
  -> join(workspace, relative_resource)
  -> normpath / abspath
  -> commonpath 校验仍位于 workspace 内
  -> 构造内存 PermissionRule
```

禁止保存：

```text
../outside
/etc/passwd
```

这不是完整的沙箱实现，但可以避免持久化层把项目外路径带入可长期恢复的 Agent 授权。

### bash 的 Agent 规则

`bash.execute` 当前没有可可靠匹配的单一资源，`resource=None` 意味着一条 Agent 规则会覆盖该 Agent 的所有普通 bash 命令。

首期建议：

```text
bash.execute 仅允许 ONCE / SESSION，禁止保存 AGENT 规则。
```

原因：持久化的 `AGENT + bash.execute + None` 等同于“此 Agent 在未来会话中默认可执行任意普通命令”，范围过大，且 UI 无法把它收窄到一个目录资源。

硬安全黑名单与受保护资源仍然会优先执行，但这不足以让持久 bash 授权成为安全默认值。未来若要支持，应先引入更细的命令能力模型，例如 `git.*`、`python.test`、`package.install`，而不是直接持久化任意 shell。

## 5. 存储模型

数据库只先建立两个表。

### `schema_metadata`

```sql
CREATE TABLE schema_metadata (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
```

初始写入：

```text
schema_version = "1"
```

用途是让未来迁移有明确入口，而不是通过“某个表是否存在”猜测版本。

### `permission_agent_rules`

```sql
CREATE TABLE permission_agent_rules (
    id INTEGER PRIMARY KEY,
    agent_key TEXT NOT NULL,
    action TEXT NOT NULL,
    resource_kind TEXT NOT NULL,
    resource_value TEXT,
    decision TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE (agent_key, action, resource_kind, resource_value)
);
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `agent_key` | 逻辑 Agent 的稳定标识。 |
| `action` | `filesystem.read` 或 `filesystem.write`。 |
| `resource_kind` | 首期固定为 `workspace_path`，提前保留资源表达方式扩展点。 |
| `resource_value` | workspace 内的相对目录或文件路径。 |
| `decision` | `allow` 或 `deny`；不允许 `ask`。 |
| `created_at` | 规则首次创建时间，仅用于管理 UI 和诊断。 |
| `updated_at` | 当前规则最后一次确认/覆盖时间。 |

表中不保存：

- `call_id`、`session_id`：它们分别属于 `ONCE` 和 `SESSION`，不应持久化。
- 绝对 `workspace` 路径：数据库文件的位置已经表达项目归属。
- 原始 bash 命令、工具输出、用户消息：避免泄漏命令中的密钥或上下文内容。

## 6. 模块与接口设计

建议新增最小持久化基础层：

```text
code/agent/
  storage/
    __init__.py
    database.py
  permission/
    repository.py
    PermissionManager.py
```

### `storage/database.py`

新增 `StateDatabase`：只负责 SQLite 生命周期、初始化和 schema migration，不包含权限领域判断。

```python
class StateDatabase:
    def __init__(self, workspace: str) -> None: ...
    def connect(self) -> sqlite3.Connection: ...
    def initialize(self) -> None: ...
    def close(self) -> None: ...
```

职责：

- 计算 `<workspace>/.harness/state.db`。
- 首次需要写入时创建 `.harness/`，目录权限尽量设为仅当前用户可读写。
- 打开连接后启用 `PRAGMA foreign_keys = ON`、合适的 busy timeout。
- 在事务中创建/升级 schema。
- 对所有 SQL 使用参数绑定，禁止字符串拼接。

不负责：

- 将行转换为 `PermissionRule`。
- 判断规则是否允许某个调用。
- 管理 Agent、Runtime 或 CLI。

### `permission/repository.py`

新增 `PermissionRuleRepository`，它是权限领域与 SQLite 的唯一交界：

```python
class PermissionRuleRepository:
    def load_agent_rules(self, agent_key: str) -> list[PermissionRule]: ...

    def upsert_agent_rule(self, rule: PermissionRule) -> None: ...

    def delete_agent_rule(
        self,
        agent_key: str,
        action: PermissionAction,
        resource: str,
    ) -> bool: ...
```

约束：

- `upsert_agent_rule()` 仅接受 `scope=AGENT` 的文件读写规则。
- 保存前将绝对 resource 转成 workspace 相对路径，并验证没有越出 workspace。
- 加载时验证 action、decision、resource_kind、相对路径和 `agent_key`；任何损坏数据都不静默跳过。
- SQLite 的 `UNIQUE` 冲突使用 `INSERT ... ON CONFLICT ... DO UPDATE`，保证同一规则槽位被新决定覆盖。
- 返回的规则一定是 `PermissionScope.AGENT`，并带请求的 `agent_key`。

`PermissionRuleRepository` 不需要设计成多个可插拔后端。首期只实现 SQLite；测试通过临时 workspace 创建真实数据库，而不是为一个实现过早增加通用仓储框架。

### 修改 `PermissionManager`

构造器增加必填依赖：

```python
def __init__(
    self,
    mode: PermissionMode,
    workspace: str,
    rule_repository: PermissionRuleRepository,
    ...,
) -> None:
```

初始化时：

```python
self._rules = rule_repository.load_agent_rules(agent_key)
```

这里的 `agent_key` 由 `Agent` 传入，或明确作为构造参数传入；不要让 Manager 从当前工具请求中“猜测”需要加载哪个 Agent 的规则。

修改 `_write_rule()` 的事务顺序：

```text
构造并验证 PermissionRule
    ↓
scope == AGENT ?
    ├─ 是：repository.upsert_agent_rule(rule) 成功后，再更新 _rules
    └─ 否：直接更新 _rules
```

如果磁盘写入失败：

- 不修改 `_rules`。
- 抛出 `PermissionStorageError`。
- Runtime 保留 pending call，不执行工具。
- UI/CLI 告诉用户“当前 Agent 授权无法保存”，用户可以改选 `ONCE` 或 `SESSION`。

这保证“用户以为已持久化允许、实际上只在内存允许”的危险情况不会发生。

### 修改 `Agent`

`Agent` 作为组装根负责创建 `StateDatabase` 与 `PermissionRuleRepository`：

```text
workspace
  -> StateDatabase
  -> PermissionRuleRepository
  -> PermissionManager
  -> Runtime
```

新增：

```python
def close(self) -> None:
    """关闭数据库连接等 Agent 拥有的本地资源。"""
```

CLI 在 `/exit` 和异常退出的 `finally` 中调用 `agent.close()`。目前 Runtime 同步运行，因此不提前设置跨线程共享 SQLite 连接；未来 Web UI 的并发模型确定后再处理连接池或任务队列。

## 7. 读取失败与安全策略

持久化权限属于安全状态，读取失败必须“失败关闭”，不能选择静默忽略。

| 情况 | 行为 |
| --- | --- |
| 数据库不存在 | 正常，视为没有 AGENT 规则；首次写入时创建。 |
| 数据库 schema 版本过新 | Agent 启动失败，提示升级程序；不能猜测解释未知规则。 |
| 表结构或规则值损坏 | Agent 启动失败，保留原数据库，提示用户修复/备份。 |
| 单条规则非法 | 同样视为存储损坏，不跳过。跳过 deny 规则可能扩大权限。 |
| 写入失败 | 当前 pending 调用不执行，用户可改用 ONCE/SESSION。 |
| 规则命中硬安全/受保护资源 | 仍分别 `DENY` / `ASK`；持久化 allow 不能绕过它们。 |

对于明确的“重置权限状态”操作，未来 UI 应删除或备份 `.harness/state.db`，但本期不在运行时自动修复、自动删除或覆盖损坏数据库。

## 8. 实施步骤

### 阶段一：SQLite 状态基础

- 新增 `storage/database.py`。
- 初始化 `schema_metadata` 与 `permission_agent_rules`。
- 添加 `.harness/` 到 `.gitignore`。
- 编写迁移和连接关闭测试。

验收：空项目首次创建 Agent 不创建无关状态；首次 Agent 规则写入后数据库 schema 正确创建。

### 阶段二：权限仓储

- 新增 `permission/repository.py`。
- 实现 Agent 规则的 load / upsert / delete。
- 实现绝对与相对 workspace 路径转换和严格读取校验。
- 增加 `PermissionStorageError`、`PermissionStorageFormatError`。

验收：规则写入后能从临时 workspace 的数据库重新读取；路径越界、非法枚举和损坏行均被拒绝。

### 阶段三：接入 Agent 与 PermissionManager

- `Agent` 创建并拥有数据库、仓储和 Manager。
- Manager 初始化加载当前 `agent_key` 的 AGENT 规则。
- `_write_rule()` 对 AGENT 规则先落盘后更新内存。
- 对 `BASH_EXECUTE + AGENT` 返回稳定的 `PERSISTENT_SCOPE_NOT_SUPPORTED` 错误。
- `Agent.close()` 关闭数据库；CLI 的退出路径调用它。

验收：同项目、同 `agent_key` 新建 Agent 后能恢复文件授权；不同 `agent_key` 和不同 workspace 都不能恢复该规则。

### 阶段四：最小权限管理入口

- 在 CLI 增加只读命令，例如 `/permissions`，列出当前 Agent 已持久化的规则。
- 再增加显式删除命令，例如 `/permission remove <id>`；删除必须要求二次确认。
- UI 实现后复用 repository 的 `delete_agent_rule()`，不要绕过 Manager 直接修改 Runtime 内存规则。

验收：用户能看见、理解和撤销跨会话规则，避免不可见的长期授权。

## 9. 测试清单

- 新建数据库、重复初始化和 schema version 校验。
- 同一规则槽位 allow 后 deny，重启后读取最新 deny。
- 同项目、同 agent_key 重启 Agent 后恢复规则。
- 同项目、不同 agent_key 不恢复规则。
- 不同 workspace 不恢复规则。
- `ONCE` 与 `SESSION` 重启后均不恢复。
- `.`, `src/`、嵌套目录等相对资源的往返转换。
- `../outside`、绝对项目外路径、错误 action/decision/scope 被拒绝。
- 持久化 allow 对硬安全路径仍为 `DENY`，对受保护路径仍为 `ASK`。
- 数据库写入失败时，Runtime 不执行 pending 工具调用。
- 两个 repository 对同一数据库连续 upsert 时，不产生重复规则或半写入。
- `BASH_EXECUTE` 选择 AGENT scope 时拒绝持久化，且不执行工具。

## 10. 后续演进

SQLite 状态库后续可以增表，但不应在本期预建：

```text
agent_profiles          # Agent 默认模式、工具集等配置
sessions                # 会话元数据
messages                # 历史上下文索引或摘要
permission_audit_events # 允许、拒绝、询问与规则修改记录
```

先完成权限规则持久化并验证生命周期，再单独设计对话历史和 UI 状态持久化。权限规则是安全状态；对话历史则是高容量、可能含敏感信息的内容，两者不能因为都叫“数据”就混在同一轮实现中。
